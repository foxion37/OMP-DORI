# Scripts

`scripts/` is a bun + TypeScript package with one CLI, `dori`. Every external command runs as an argv array; nothing builds a shell string.

The CLI loads only the selected command graph, including its existing dependencies. `--version` needs no command/configuration graph; `harness`, `update` and `upstream` retain their separate entry paths. Ordinary commands, including journals and usage, still load and validate configuration and consumer-native dependencies before command execution. Lazy loading does not skip native integrity checks. Errors retain their original classes, messages and exit codes.

## Install and test

```sh
cd skills/dori-mode/scripts
bun install          # dev dependencies only (types, tsc)
bun link             # puts `dori` on your PATH
bun test             # behavior tests with fake herdr/hc/git/gh; nothing real is touched
bunx tsc --noEmit    # typecheck
```

Needs: Bun 1.4.4+, the installed default OMP source bundle (18.20.0), herdr or hc, git, and the GitHub CLI (`gh`) for `merged`/`closed` signals (npm for `published`). An explicit external OMP is an advanced override, not bundle proof; historical published `v0.1.2` keeps its 18.18.8 contract. The `command`, `file` and `url` signals need nothing extra. The host guard reads `sysctl`, `memory_pressure` and `df` on macOS; on Linux it reads `/proc/loadavg` and `/proc/meminfo` (`MemAvailable` over `MemTotal`) directly in-process, then runs `df` and the selected runtime's session list. Linux no longer spawns `cat` or attempts the macOS-only probes; non-Linux command probes and their fallback behavior are retained. Host memory counts as 100% free when neither source works, and swap reads as unknown on Linux.

On Linux, `sampleHost` also exposes `cgroup`: the tightest visible ancestor hard-limit headroom and, for v2, a separate `memory.high` headroom. `guard` and `can-launch` apply `memFreeMinPct` independently to host memory and both budgets; a roomy host never overrides a constrained account. The sampler resolves `/proc/self/cgroup` through `/proc/self/mountinfo`, reads each ancestor's own current usage, and stops at the mount root. It supports v2 `memory.max`/`memory.high` and hierarchical v1 `memory.limit_in_bytes`; v1 soft limits are not v2 throttling limits and are not used. Unlimited limits are ignored. Zero limits have zero headroom, and admission uses the unrounded percentage.

Each budget retains raw `currentBytes` and `chargedFreePct`. Admission uses `freePct`, an available-budget estimate that subtracts clean, unmapped file cache from current usage: `max(0, file - shmem - file_mapped - file_dirty - file_writeback)`, capped at current usage. This prevents ordinary file caching from permanently holding a constrained account. It does not treat shared, mapped, dirty, writeback or kernel pages as free, and it is an estimate rather than an allocation guarantee. v1 uses `cache`/`mapped_file` and the matching local or `total_*` counters according to `memory.use_hierarchy`. Missing or malformed cache statistics set `cgroup.incomplete` and keep the raw charged budget as the conservative fallback. Missing limit or usage readings also set `incomplete`; readable budgets still apply, and unavailable budgets retain the existing host fallback rather than becoming an invented zero or unlimited value. No supported cgroup membership yields `version: null`. A resolved v2 hierarchy retains `version: 2` when memory interface files are absent: missing non-root limits set `incomplete: true`, while absent interfaces at the hierarchy root are expected. A fully readable unlimited hierarchy has null budgets with `incomplete: false`. Cgroup namespaces can hide outer ancestors, so only the visible hierarchy is covered. macOS does not read cgroup files.

## Lane status and one-message boards

`dori status [<key>] [--json]` reads open lanes, or one named lane including a closed lane. It joins registry state, PID/session-verified OMP runtime state, report/checkpoint journals, open decisions and recorded monitor metadata. Unreadable registry files and invalid status fields are isolated with `registryIncomplete: true`; healthy lanes remain visible, and an empty incomplete view is unknown rather than "none open". Each source keeps its timestamp; unavailable runtime or journal observations are unknown, not idle or zero. Runtime identity must also match the lane's recorded session binding (`sync --write` establishes it); an unbound lane is unknown even if its pane contains a live agent. Damaged decision or monitor metadata makes its count unknown rather than reporting the remaining readable subset as a complete count. Monitor flags and expiry values are validated before counting. Legacy argv that boot can match through command still makes status counts unknown when malformed. Monitor metadata does not prove a process is running. The last sweep note and nudge/post timestamps are recorded evidence, not a prediction of the next freshness action. Status never runs a sweep, writes journals, sends messages or reads private session transcripts.

`dori eta <key-prefix> [--json]` summarizes historical opening-to-close elapsed minutes for that explicit prefix. Fewer than three valid closed lanes produces no estimate; otherwise the median, range and sample count are shown. An incomplete registry also suppresses the estimate and identifies the readable sample count. This is not a completion promise.

Start a board only when its destination is authorized:

```sh
dori board discord --thread 123456789 --loop 2
dori board telegram --to -100123456789 --thread 42 --loop 2
```

The existing `DORI_DISCORD_TOKEN` or `DORI_TELEGRAM_TOKEN` supplies authentication. Discord accepts numeric channel IDs with `--to` or a thread ID with `--thread`; Telegram requires a numeric chat ID. `--lane KEY` limits the view. Omit `--loop` (or set it to `0`) for one update; a positive value is minutes. No board starts with installation, boot, status or launch. Supervise the command with a native monitor if desired; stopping that monitor stops updates.

The board rejects unsupported options or extra positional arguments. A supplied `--lane` must name exactly one valid lane; it never falls back to all lanes.

Each destination owns one private `<stateDir>/boards/<sha256>.json` record. A lock serializes writers, and the message ID survives restart. Unchanged content sends nothing; changed content edits that message, never splits it. The bounded summary scrubs local paths and pane IDs, neutralizes mentions, and states when lanes were omitted. HTTP(S) evidence links retain their origin and path, not URL userinfo, query strings or fragments. Because spaces can belong to an unquoted path, text from a local path to the end of its non-URL segment is omitted conservatively. Its timestamp is the last successful content update, not a heartbeat: a stopped updater leaves that timestamp unchanged.

Before a send/edit, a durable pending record is written. An ambiguous create or any failed edit stops the command and holds future calls rather than creating another message. A definitively rejected initial create (HTTP/API 4xx, including exhausted 429 backoff) removes only its own uncreated intent; after correcting permissions, a new explicit invocation can create the board. There is no automatic resend. Even an edit with a known ID requires explicit acknowledgement after failure: inspect the destination and pass `--message ID`. Discord scopes an edit to the selected channel. Telegram edits identify only the chat and message, not the topic, so a Telegram recovery ID must already be recorded for the exact board destination. An ambiguous Telegram create without a recorded ID stays pending; the command cannot safely attach an unbound ID. A missing message is not automatically replaced. Do not delete a pending record or retry a create merely because the response was lost. API acceptance is not proof that the owner read the board.

## Configuration

`~/.dori/config.json` (or the path in `DORI_CONFIG`). Every field is optional; see `config.example.json`. `DORI_STATE_DIR`, `DORI_LEAD_PANE` and `DORI_RUNTIME` override the file.

| Field | Default | Used by |
|---|---|---|
| `runtime` | detected | every command that opens or reads a session: `"herdr"` or `"hc"`. Unset, the Dori picks hc inside an hc terminal (`HC_TERMINAL_ID`), herdr inside a herdr pane (`HERDR_PANE_ID`), else hc when it is on PATH, else herdr, and refuses only when neither is there. Lanes already open stay on the runtime that opened them |
| `stateDir` | `~/.dori/state` | registry, heavy slots |
| `laneWorkspace` | current workspace | `launch`: the herdr workspace, or on hc the `dori.group` label (default `dori`) |
| `workspaces` | all | `sync`, `dead-panes`: herdr workspaces, or `dori.group` labels on hc |
| `ignorePanes`, `leadPane` | none | sessions the sweeps skip, by id (`w1:p3` on herdr, `t7` on hc); `leadPane` is also where lanes report |
| `defaultCwd` | home | where lanes start, and the repo whose worktrees they own |
| `agentCommand`, `defaultModel`, `launchKeywords` | `omp --dori-role lane --model {model} {prompt}`, `anthropic/claude-opus-5-5`, `ulw set goal and work` | `launch`; explicit configuration remains authoritative |
| `goalMarker` | `Pursuing goal` | launch goal-check policy; OMP activity is confirmed from the trusted extension goal record, while an explicitly empty marker keeps upstream's opt-out |
| `startupWaitSeconds` | 180 | `launch`: how long after the start it waits for the agent's ready status and goal; raise it on a slow host. A value that is not a nonnegative number uses the default |
| `sessionsDir` | `~/.omp/agent/sessions` | OMP session-id lookup |
| `ompUlwPath` | `~/.dori/omp-ulw/index.ts` | nonempty paths retain the role-gated import; consumers use their manifest-bound cache pin, while `scripts/install-source.sh` sets `""` and loads the selected checkout once as an OMP extension (globally for primary, explicitly for side) |
| `nudgeAfterMin`, `postAfterMin` | 15, 20 | `freshness` |
| `closeAfterMin` | 5 | `watch` |
| `contextClaudePattern`, `contextHandoffPct`, `contextHandoffPctOther` | `claude\|opus\|sonnet\|haiku`, 40, 60 | `context`: models matching the pattern count as high at the first percentage, others at the second |
| `contextUnknownAfterMin`, `relayTimeoutMin` | 10, 10 | `context` (`CONTEXT_UNKNOWN`), `relay` (how long the handoff may take) |
| `heavySlots`, `heavyMaxLoad` | 1, 80 | `heavy` |
| `deadPanePatterns` | `has stopped`, `no suitable jobs` | `dead-panes` |
| `guard` | load 150/80, 20% memory, 50 GB disk, 20 panes | `guard` |
| `hooks.threadReply`, `hooks.threadDone` | none | `freshness`, `close` |
| `hooks.transcribe` | none | `transcribe` (argv with `{file}`, prints the text) |
| `transcribeMaxBytes` | 26214400 (25 MiB) | `transcribe` HTTP(S) URLs: positive safe integer cap on actual streamed bytes; local files are unchanged |
| `supervision` | no ceilings by default (set wallMinutes, tokens or costUsd to enable); hung after 20 min | `freshness`, `launch`, `close` (see Supervision below) |
| `repoIdentities` | none | `verify-pr`, `launch` footer: expected Git name and email per `owner/repo` (keys match without case) |
| `prAutoTrack` | `false` | `claim-done`, `checkpoint`: when `true`, pull-request links in a recorded claim's evidence or a checkpoint's `--remote-effect` receipts are tracked for `dori pr watch` with the lane and its thread. Any value other than `true` or `false` stops every command with `invalid prAutoTrack` |

Hooks are argv templates for your messenger CLI. `{thread}`, `{text}` and `{key}` are filled into each argument separately, so the text stays one argument whatever it contains.

## Read-only diagnostics

`dori doctor [--json] [--repo owner/repo]` checks the selected home's configuration, registry, worklog, lessons, desired monitor metadata and trusted live lead. It exits 1 when a visible WARN remains, otherwise 0; INFO is advisory. It never edits config, starts/stops a monitor, invokes a hook or usage reader, contacts a messenger, or reads private session transcripts. Local runtime/process probes are read-only. `dori boot` includes a local `DOCTOR warn=N` advisory without changing boot's existing exit policy.

Checks are identified by `runtime`, `registry`, `monitors`, `monitor-filter`, `monitor-runtime`, `supervision`, `repo-identities`, `worklog` and `lessons`. Optional `doctor: { "ignore": ["lessons"] }` suppresses named diagnostics; the selected ignore list remains in doctor output. Nothing is ignored by default. Repository identities are checked for open lanes' merged/closed repository signals and the optional `--repo`; doctor does not guess a GitHub repository from a directory name.

`dori monitor-presets [watch|dead-panes|guard|freshness|pr-watch] [--json]` prints recommended structured argv and filters, starting nothing. Review the preset and restart only the explicitly authorized monitor in its owner session. Side installations must use their own bound CLI/PATH. Only the trusted current lead's filter produces WARN; historical or unverified owners stay INFO, so old manifests do not keep doctor failing after an upgrade. Filter diagnostics recognize direct `dori`, `omp-dori`, and `bun .../dori-mode/scripts/src/cli.ts` argv, even when the monitor was renamed; arbitrary shell scripts are not inferred from their name. The probes detect missing event categories, not every possible restriction in a custom regex.

Desired specs alone are not evidence that a child is running. Only the current trusted Dori process, a fresh matching runtime receipt and the child's PID/start identity establish liveness. Other sessions' recorded monitors stay INFO with liveness explicitly unverified; stale, unreadable or mismatched current-lead receipts warn rather than claiming that a monitor is healthy. Doctor does not recommend an unattended restart.

Doctor checks unreadable legacy terminal metadata under the same `PI_SESSION_DIR` or `PI_SESSION_FILE` roots as `dori boot`; those records cannot attest native monitor liveness. A native receipt must also match the desired restart policy, including when no restart policy is set.

Malformed lane keys are counted without being printed. Unrecognized status or approval values in a trusted lead record appear as `unknown`; a record that fails the runtime trust checks does not attest a live lead.

Every module takes its HTTP, clock and timers as arguments. That is how the tests run without the network.

`discordInboundLive` adapters expose `cursorFor(channel)` from their injected store. `storeFor(channel, false)` reads admission state without seeding an unseen channel; wrappers must forward that optional argument. An admission position is not a delivery receipt.

Slack commits a successful poll's own-thread cursors in one ledger transaction, only after all reads and emits finish. `ThreadLedger.markSeen` takes the authenticated `SlackScope` and an array of `{ channel, rootTs, ts }` updates and merges them under the existing writer lock; concurrent thread records survive and seen positions never decrease. Empty batches do not take a lock, and batches with no newer known cursor do not rewrite the ledger. This does not reduce Slack requests or stop watching older threads.

## Commands

### `dori launch <key> --title T --brief FILE --done "..." [--thread REF] [--model M] [--cwd DIR] [--group NAME] [--dry-run]`
Opens a lane: puts current global and repository lessons above the brief, appends the footer, creates the runtime session and starts OMP. After 20 seconds it checks the unwrapped screen for known startup failures, including OMP extension/flag/model errors. Provider failure phrases are distinguished from code, paths and lane names; a custom omo agent's recoverable missing-extension warning is ignored, but a real failure beside it still counts. `STARTUP_OK` requires a ready runtime status (idle, working, or herdr's `done`) and an active goal from the live-process-bound OMP extension record; goal state is independent of terminal width, and an approval or shell never counts as ready. Custom agents retain their own goal record or footer-marker check. An explicitly empty `goalMarker` opts out of the goal check, not readiness. The status and goal are rechecked every 10 seconds until `startupWaitSeconds` (180 by default) after start, including while an agent has not reported a status yet. A running agent without a confirmed goal reports `STARTUP_NO_GOAL`; missing readiness is `STARTUP_UNCONFIRMED`. Lookup errors, shells and known failures end the wait immediately. A gone session whose lane is already closed, verified-done or journal-done is `STARTUP_DONE <key>`. Exit 0 on `STARTUP_OK` or `STARTUP_DONE`, and 3 otherwise.

The lane never gets the Slack token itself: on hc every env value is a command-line argument, which `ps`, `hc get` and logs show. When the launcher has `DORI_SLACK_TOKEN_FILE`, or a `slack-token` file sits next to its config, the lane gets that path as `DORI_SLACK_TOKEN_FILE` and an empty `DORI_SLACK_TOKEN`, so a token inherited from another home's core cannot win. The path is passed absolute. A `DORI_SLACK_TOKEN_FILE` outside the launcher's home (its config's directory) is most likely inherited from another home, so the launch refuses it (`token file refused: ...`) unless `DORI_SLACK_TOKEN_FILE_OUTSIDE_HOME=1` says it is meant; links are resolved first, and the flag is passed to the lane empty. `dori boot` refuses such a path the same way. With neither, the Slack environment is unchanged. Independently, launch always sends empty `DORI_DISCORD_TOKEN` and `DORI_TELEGRAM_TOKEN` overrides so terminal-server tokens cannot leak into lane agents; an explicitly authorized messenger child must load its own token. Empty tokens are rejected before any messenger network request.

`--dry-run` prints the brief as the lane would get it, lessons and footer included, and changes nothing.

Label: every lane shows one label, derived in `src/labels.ts` from its `--thread` and `--title` and stored on the lane record as `label`: a lane opened from a Discord thread is `DICO : <title>`, one from Telegram `TLGR : <title>` (uppercase ticker, space, colon, space, then the task name), and a lane opened outside a thread is its bare title. dori puts it on the tab or workspace it creates for the lane, renames a split pane to it, and passes it to the agent as `DORI_LANE_LABEL`; the omp-dori extension names the omp session after it at session start, so the conversation in the session shows the same label. A workspace dori did not create and a tab shared with another lane of the group keep their own label. `adopt` records the label but renames nothing.

Placement: without `--group` the lane gets its own tab in `laneWorkspace`. With `--group NAME`, an open lane of that group makes the new lane a split below that group's newest lane, in the same workspace; with none open, dori creates a workspace for the group. The lane record keeps `group`, `placement` (`tab`, `split`, `workspace`), `workspace`, and `workspaceCreated` when dori made the workspace. Different project or account: a different group, so its own workspace. Side work on the same project: the same group. On hc, which has neither workspaces nor splits, every lane is one labelled terminal and the group is that label.

New launches record `launchSelection` in the registry and footer: `invocation` is the unchanged `launchKeywords` text, `selectedBy` is `default` (built-in), `config` (an explicit setting, including an empty string), or `provided` (programmatic configuration without matching load provenance), and `reason` identifies that origin. The configuration loader derives the origin, including the loaded file path, rather than trusting a supplied metadata field or rereading a file after it changes. Older and adopted lanes have no invented historical selection.

`selectedBy` describes the provenance attached to matching invocation text, not assignment history. A file that explicitly supplies the built-in text is still `config`. Spreading a default or loaded configuration and assigning the same text again retains its matching `default` or `config` origin; the normalized object cannot identify that reassignment. Without matching provenance, the source is `provided`.

This is requested-selection metadata, not proof of native activation, delivery or goal creation. The default remains `ulw set goal and work`; prompt bytes, raw `tell` delivery and startup goal checks are unchanged. Workflow names in a brief, quoted example or path do not choose this metadata. Native OMP/ULW still owns activation and workflow semantics; there is no new per-lane workflow switch.

The footer uses the already selected runtime (`DORI_RUNTIME` > config > detection) for its report-forwarding command. It binds reports to this skill's CLI path and carries `kind`, `text` and the printed line as data arguments; supply values through environment variables or proper shell quoting, never by interpolating raw text into executable source. Before forwarding, verify the live agent, empty input and absence of approval/question prompts as described in [Messaging a session](sessions.md#messaging-a-session), then confirm delivery from a status transition or session record. Report text containing shell punctuation is still data, including when expanded through `"$line"`. If the lead pane or runtime is unavailable, the footer records and prints the report without a forwarding command. Preview runtime selection reads configuration/environment/PATH metadata and never starts a runtime.

Sol lane main agents are encouraged to batch bookkeeping already required by the task and supplied launch footer. Checkpoints, reports, forwarding and claims remain mandatory when due; failed prerequisites stop dependent commands, and partial chains stay incomplete. A same-data checkpoint retry returns the existing record; a conflicting rewrite fails, and remote effects must never be replayed just to retry their journal entry. Strict one-line harness reviewers without a launch footer keep that output contract. The author's n=5-per-arm comparison used stubbed reporting/delivery on an earlier tree; it is not a reproduction or proof of turn or wall-time savings on the integrated tree.

### `dori adopt <key> --pane ID --title T --brief FILE --done "..." [--thread REF] [--group NAME]`
Registers a lane that is already running. `--group` records the group and the session's workspace; a workspace someone else opened counts as not created by dori, so it is never closed.

### `dori context [--loop MIN] [--relay]`
Reads each open lane's model and context use from its pane state file (written by the omp-dori extension at session start and each turn end; only a record the session's own live agent vouched for counts). A model matching `contextClaudePattern` is high at `contextHandoffPct` (40), any other at `contextHandoffPctOther` (60). Prints `CONTEXT_HIGH <key> <pane> <model> <pct>%` once per crossing; the lane record remembers it until usage falls back under the threshold. The lead session is reported as `CONTEXT_HIGH lead ...` and never relayed. A lane with no context data `contextUnknownAfterMin` (10) minutes after it opened or was last relayed prints `CONTEXT_UNKNOWN <key> <pane>` once. With `--relay`, a crossing starts `dori relay` for that lane; a failed relay is not retried until the crossing resets, a skipped one is reported once per reason.

### `dori relay <key>`
Hands a lane to a fresh session. It sends the lane a `[LEAD]` message to stop new work and write a handoff to `<stateDir>/handoffs/<key>-<n>.md` (goal, done and not done, evidence, files/branches/SHAs, next steps, no secrets), then waits up to `relayTimeoutMin` (10) for the file; on timeout it prints `RELAY_FAILED <key> handoff not written` and changes nothing. Then it splits a new session below the lane's, starts the same agent command and model with the brief and handoff in the prompt, and runs the launch startup check. On `STARTUP_OK` the registry takes the new session (`relays`, `previousPanes`, placement `split`), the old session closes, and it prints `RELAYED <key> <old> -> <new>` (exit 0). On a failed start the new session is closed, the old lane is untouched, and it prints `RELAY_FAILED` with the startup line (exit 3). A lane that is not working, a closed one, or one with an approval prompt open is `RELAY_SKIPPED` (exit 2) and nothing is sent.

### `dori sync [--write]`
Prints `key | thread | pane | session | status` for every open lane and every unregistered agent pane, followed by drift. Read-only unless `--write`, which stores session ids.

### `dori report <key> --kind milestone|blocker|question|halted|done --text TEXT`
Run by a lane. Appends one record to `<stateDir>/lanes/<key>/reports.jsonl` and prints the `[REPORT] <key> | <kind> | <text>` line the lane then sends to the lead pane. Each record is a single append, so the lane and the lead can write at the same time without losing one. The last record is the lane's progress state: `milestone` is running, `blocker` and `question` blocked (a question waits on the owner's answer), `halted` halted, `done` done. The screen grammar takes the same five kinds. Text stays data: newlines are folded into the printed line, never into the journal. A corrupt journal is an error with its line number, never an empty state. Lanes opened by `dori launch` are told to report this way and are marked `reportProtocol: "jsonl-v1"`; launch starts their journal with a `running` activity record, which is not a report and is never posted.

`--owner SUMMARY` stores a separate owner-facing summary; the lead detail remains in `text` and the default printed line. `--json` prints the full report plus its content-bound `id` instead of the human line. Summaries must be nonempty, and receive the same terminal-control and local-path scrubbing before automatic posting. Existing reports without a summary remain readable.

### `dori relayed <key> --report ID`
After actually delivering a report to the owner, the lead acknowledges the exact `id` returned by `report --json`. This command sends nothing: it records the receipt and updates that lane's thread-quiet clock, without changing its nudge clock. A missing, replaced or non-journal report is refused, even if the newer report has the same timestamp. It does not resolve a blocker or change completion status. An ordinary messenger send is not proof that a particular report was relayed; use this explicit receipt after delivery.

### `dori boot`
Run by the lead after a restart or a compaction, before it trusts what it remembers. It is read-only: it writes no registry record, relaunches nothing and stops no watch. It prints:
- `RUNTIME <kind> (from <source>)` first: the runtime new lanes open on and why (`env`, `config`, `detect:HC_TERMINAL_ID`, `detect:HERDR_PANE_ID`, `detect:path`). `RUNTIME unavailable: <fix>` when none can be chosen, and boot then exits non-zero.
- `SLACK authenticated user=... team=...` from `auth.test` when `DORI_SLACK_TOKEN` is set or `DORI_SLACK_TOKEN_FILE` names a token file (`SLACK skipped` otherwise). A token file that is missing, unreadable, not a regular file, owned by another user, empty or open to group or others is `SLACK token-file: <reason>`, naming only the path, and fails the boot. This proves the token, not that messages arrive. It runs last, after the local checks below, and gives up after 10 seconds (`SLACK auth.test timed out after 10000 ms`). A response without a user or team id is `SLACK auth failed`.
- `PANES` with the lead pane's state, then `VANISHED <key> pane=...` for each open lane whose pane is gone (a `verified-done` lane is not flagged), and `UNREGISTERED <panes>` for panes no lane owns. Sessions are listed on every runtime a lane lives on (`herdr pane list` / `hc ls`); if that list fails, no lane is called vanished.
- `DRIFT n=<count> <keys>`: lanes not finished (`closed`, `verified-done`, or a `done` report, the lanes `VANISHED` skips too) whose session the runtime's own probe reports gone (`herdr pane get`, `hc get`). Only lanes missing from the session list are probed. Any drift fails the boot; a probe that errors is `DRIFT probe-failed <key> (...)` and also fails it.
- `CONFIG_WARN workspaces=[...] does not include laneWorkspace=...` when `config.workspaces` is set and leaves out `laneWorkspace`, or `CONFIG_WARN workspaces=[...] match none of the <n> live agent sessions ...` when live agent sessions (in `laneWorkspace` when it is set, the lead and `ignorePanes` aside) exist and none is in `config.workspaces`: `dead-panes` and `sync` filter on that list and would watch nothing. Checked only on a runtime with workspaces (herdr; hc has none). It fails the boot.
- `REPORT <key> kind=... at=... state=...` for each launched (`jsonl-v1`) lane's last report, next to its registry status, since the two can disagree after a crash. A journal that holds only records dori wrote itself (the launch, a screen-detected stall) is `NO-REPORT <key>`, never a report, and a launched lane with no `reports.jsonl` yet is `NO-REPORT <key> ... (no journal)`. An adopted lane's journal is not read, as in `freshness`. An unreadable journal is `JOURNAL-ERROR <key>: ...` for that lane only; the other lanes are still checked.
- `WORKLOG open=<n>` and an `OPEN <id> "<title>" source="<ref>" next="..."` line for each open worklog item (see `dori worklog` below).
- `DECISIONS open=<n>` and a `DECIDE <id> age=<h>h lane=<k|-> thread=<ref|-> "<question>"` line for each open owner decision, only when `<stateDir>/decisions.jsonl` exists (see `dori decision` below).
- `CLEANUP <keys> match=...` and an owner-session-only stop command for persistent watches tied only to finished lanes (closed, verified done, or a `done` report). OMP manifests are read from `<stateDir>/monitors/<encoded session id>.json`; exact argv tokens tie a watch to a lane, and any mention of an open lane keeps it. OMP cleanup uses `monitor({"op":"stop","name":...})` in the owning session. Original terminal-manifest discovery and its `kill_bash(...)` recommendation remain available for that metadata format. Boot never opens private session transcripts or stops a watch. Expired terminal watches remain `EXPIRED` with nothing to stop, and unreadable metadata remains an explicit `MONITORS unreadable` error.

Exit 0 ends with `BOOT checked`. A lane file that cannot be read or parsed, or a lanes path that cannot be listed, is `REGISTRY unreadable <path>`; the other lanes are still checked. Any input that could not be read (Slack, the registry, panes, a journal, the worklog, the decisions, metadata) is printed and gives `BOOT incomplete`, exit 1.

### `dori checkpoint <key> --step ID --result TEXT --evidence PATH [--remote-effect RECEIPT]...` / `dori checkpoints <key>`
Run by a lane after each completed step, and on resume before doing work. Each step is one line in `<stateDir>/lanes/<key>/checkpoints.jsonl` with its result, evidence and the receipts of remote effects it completed (a push, a merge, a deploy). Recording the same step again with the same data returns the original, unchanged; different data for a recorded step is refused, and so is a receipt another step already recorded. Writes fsync the journal (and its directory when they create it) under a lock file, `checkpoints.jsonl.lock`, that records the writer's pid, host and time. A live writer's lock is refused with its pid and age. A lock whose pid is dead on this host, or that is two minutes old, is taken over, so a writer killed mid-write never locks the lane.

A lane reads its checkpoints before resuming and never repeats a recorded remote effect. A crash between a remote action and its checkpoint is not covered by the journal: read the live remote state first, and use the service's idempotency key where it has one.

### `dori verify-pr <owner/repo> <num> [--loop N] [--cwd DIR]`
Run before a lane claims PR work done. It reads the PR through `gh api` (the PR, every commit with all of its files, the PR's files, then the PR again) and checks:
- every commit's author and committer email is the one in `repoIdentities` for that repo, ignoring case. The name may differ. `noreply@github.com` is accepted only as the committer of a merge commit, even if it is the configured email. A repo with no configured identity fails before anything is read; `loadConfig` drops an entry whose `name` or `email` is not a nonempty string, so such a repo counts as unconfigured;
- a PR with `fix:` or `fix(<scope>):` commits (with or without `!`) that touch source changes at least one test. A test file counts when GitHub lists it as added, modified, renamed, copied or changed (not removed) and it is named as a test (`*.test.*`, `*.spec.*`, `test_*.py`, `*_test.go`, `*_test.py`) or sits in a `test`, `tests` or `__tests__` directory. Nothing under a `fixtures`, `__fixtures__`, `__snapshots__`, `helpers`, `fakes` or `mocks` directory counts. In a test directory, a file that is not named as a test does not count when its name is `setup`, `conftest`, `test-utils`, `fixture(s)`, `helper(s)`, `fake(s)` or `mock(s)`, or when it sits in a `setup`, `conftest` or `test-utils` directory; a file named as a test (`test/setup.test.ts`, `test/helpers.test.ts`) counts. A body line `No test: <reason>` waives this. A fix commit without its own test is a warning, since its test may be in a later commit.

If the head, body or commit count changed between the two reads, or GitHub's answer is incomplete, the result is `FAIL`. Each `gh api` call is killed after 120 seconds, which is also a `FAIL`. Changed UI tests (`.tsx`/`.jsx`, a `ui`, `component(s)`, `feature(s)`, `e2e`, `browser` or `playwright` directory, or DOM calls in the patch) are listed with a shell loop that runs them `--loop` times (default 20) at the reported head. dori never runs the loop. `PASS` exits 0, `FAIL` exits 2.

### `dori pr track <owner/repo#N|pull-url> [--lane K] [--thread REF]` / `pr untrack <ref>` / `pr list` / `pr watch [--loop MIN] [--ignore-author LOGIN]... [--self LOGIN]`
Follow a pull request after the lane that opened it has closed: reviews, CI failures, commits someone else pushed to its branch, and its merge. `track` takes `owner/repo#N` or a `https://github.com/owner/repo/pull/N` link and prints `PR_TRACKED <owner/repo#N> lane=<key|-> thread=<ref|->`. `--lane` must name a registered lane (open or closed); its thread is used when `--thread` is not given (a lane launched without a thread, recorded as `none`, gives none, and `--thread none` also means no thread). A lane key or thread is one token, without spaces or control characters, because both are printed inside the event lines. A PR is one record however its owner and repository are cased. Tracking a tracked PR again replaces its lane and thread and keeps its cursor; if the watcher already saw it merge or close, it is read once more. `untrack` ends the tracking and prints `PR_UNTRACKED`, or `PR_NOT_TRACKED`; tracking it after that starts from a new baseline, even if no pass ran in between. `list` prints the tracked PRs as JSON with `since` (when this tracking began), `trackedAt` (the latest track) and the watcher's last head, state, read time and number of known items (`watch: null` before the first read, or after a `PR_WATCH_WARNING` that the cursor file is damaged).

With `prAutoTrack: true` (default `false`), a recorded `claim-done` tracks every pull-request link in its evidence, and a `checkpoint` every link in its `--remote-effect` receipts, for that lane and its thread. Only full `https://github.com/<owner>/<repo>/pull/<N>` links count; `owner/repo#N` in free text may be an issue and is not taken. A link already tracked for the same lane and thread writes nothing, so a repeated receipt does not make a merged PR read again. The `PR_TRACKED` lines go to stderr. A tracking failure prints `PR_TRACK_WARNING <reason>` on stderr and never changes the claim or checkpoint, which is already recorded.

The record is `<stateDir>/pr-watch.jsonl`, one append per change, so the lead and a lane can track at once; a write cut off halfway is skipped quietly, and other damage is named (`PR_WATCH_WARNING` from `list`, and once per damaged line `PR_WATCH_WARN - tracking record damaged: ...` from `watch`).

`watch` needs `gh` with read access to the repositories. It prints `PR_WATCH_READY`, then every `--loop` minutes (once with no `--loop`) reads each tracked open PR through `gh api`: the PR, its review comments, conversation comments, reviews, its commits when the head moved, and the check runs and combined commit status of the head, every page of each. The first read of a PR is a baseline: `PR_WATCH_BASELINE <pr> lane=... thread=... head=<sha7> state=<state> known=<n>`, and nothing already there is reported. After that each new item is one line, once:
- `PR_FEEDBACK <pr> lane=<key|-> thread=<ref|-> kind=<review-comment|comment|review-<state>> by=<login> <url> | <excerpt>`. A review counts when it is submitted in any state but a bodiless `COMMENTED` (its words are in its review comments), and again when its state changes, as when an approval is dismissed (`kind=review-dismissed by=<reviewer>`). A branch rule that dismisses stale approvals on every push therefore prints a line per dismissed approval. Pending reviews never count. Edits to an existing comment or review body are not news.
- `PR_HEAD_MOVED <pr> lane=... thread=... by=<logins|unknown> +<new commits> <old7>..<new7>[ rewritten] <pr-url>` when the head moved with commits by someone other than us, or with no new commit at all. A commit's people are its author and committer; GitHub's `web-flow` web committer is not a person. A Git identity linked to no GitHub account counts as ours when its email is one of the configured `repoIdentities` emails, and otherwise prints as `unknown`; emails are never printed. `rewritten` means the old head is no longer in the PR, as after a force-push. Our own pushes print nothing. GitHub lists at most 250 commits of a PR; past that the new commits come from a compare of the old head with the new one. If GitHub no longer has the old head (the compare answers HTTP 404, as after a force-push), the line is `by=unknown +0 ... rewritten`; other compare failures are retried like any failed read.
- `PR_CI_FAIL <pr> lane=... thread=... conclusion=<conclusion> head=<sha7> <url> | <check name>` for a check run concluding `failure`, `timed_out`, `cancelled`, `action_required` or `startup_failure`, or a commit status in `failure` or `error`, on the current head. A rerun that fails again is a new check run and a new line. Failures already there at the baseline are not repeated.
- `PR_MERGED <pr> lane=... thread=... sha=<merge sha>` or `PR_CLOSED <pr> lane=... thread=... unmerged`, also at once for a PR already closed at its baseline. A merged PR is not read again unless it is tracked again. A PR closed unmerged costs one read of the PR per pass until it is untracked; when it reopens, `PR_REOPENED <pr> lane=... thread=...` follows what arrived meanwhile, and it is followed as before. If it was reopened and merged between two passes, what arrived meanwhile and `PR_MERGED` are printed instead.

"Us" is the `gh` account (`gh api user`), or `--self LOGIN`. Until it is known, nothing is read and `PR_WATCH_WARN self holding: ...` is printed once, since every push of ours would otherwise look like someone else's. Comments and commits by us or by an `--ignore-author` login (repeatable, case-insensitive, for bots) are marked seen without a line. Text from GitHub is data: logins, kinds and check names are folded to one token, excerpts to one line of at most 160 characters with control, line-separator and bidirectional-control characters removed, and a URL that is not one clean `https://` token prints as `-`.

The watcher's cursor is `<stateDir>/pr-watch-state.json`, written through a temp file and rename after the pass's lines are printed, so a crash in between prints a line again rather than losing it. Run one `pr watch` per state directory, as with `watch` and `freshness`. A failed read (a `gh` error or timeout after 120 seconds, an incomplete answer) changes nothing for that PR and prints `PR_WATCH_WARN <pr> <reason>` once per distinct reason until a read succeeds (for a PR closed unmerged, its one read); what arrived meanwhile is reported then. A commit list that holds the head read just before it anywhere but last, or lacks it while shorter than GitHub's 250-commit cap but not empty (a push during the read), is read once more, so a head is never saved with another head's commits; a branch still moving then is read again on the next pass. A cursor file that cannot be read or is damaged holds every pass with `PR_WATCH_WARN state holding: ...` and is left in place, never reset to a new baseline that would hide events. Any other failure of a pass (an unreadable tracking record, a cursor that cannot be saved) is `PR_WATCH_WARN run <reason>`, once per distinct reason. Each pass costs six `gh api` calls per open PR, more when the head moved or a list runs past 100 rows, and one per PR closed unmerged; five open PRs every three minutes is about 600 calls an hour, within GitHub's 5,000 hourly limit for an authenticated user. A list of exactly 3,000 rows is read whole; a longer one is refused rather than read in part.

### `dori claim-done [<key>] --evidence TEXT` / `dori object-done <key> --reason TEXT ...`
The two halves of the done flow. Both message the lane's pane and check that Enter registered.

Lane records change under a per-lane lock, and a status change applies only if no other status change (a claim, objection, verification, pause, resume or close, including a second objection to a `not-done` lane) landed since the command read the lane. Otherwise nothing is recorded: `claim-done`, `object-done`, `close`, `pause` and `resume` print `LANE_CHANGED <key> moved on while this ran (now <status>, was <status>); <change> not recorded` and exit 3. Read the lane again and decide anew.

### `dori lanes [--thread REF] [--open]`
Lists registered lanes as JSON with their key, title, exact thread reference, status and open/close times. `--thread` matches the complete stored reference; use one consistent reference for lanes sharing a work thread. `--open` excludes only `closed`, so paused, blocked-progress, not-done and unverified claims remain visible. It changes no records.

### `dori close <key> [--note TEXT]`
Set `"threadDonePolicy": "last-lane"` in the config to run `threadDone` only when the final registered member of that exact thread closes. Every non-closed member holds the hook. Close, park, abandon and reopen of an existing member acquire its lane delivery lock before the shared thread lock. The thread lock serializes the election and registry commit, including native pane confirmation for a reopened close. Park and abandon hold it from before the native pause or close through the terminal receipt; reopen holds it through pane creation and registration of the new paused generation, not startup, goal resume or note delivery. The recorded native session and its files are preserved across park/reopen. Thread hooks, cost recording and later cleanup run outside the lock. An unreadable or malformed membership row blocks election.

A live thread lock held beyond 30 seconds prints `HELD <key> thread close in flight (...)` (manual close, exit 2) or `LANE_HELD ...; retried next tick` (watch). A claim verified while waiting stays open for boot monitor cleanup. An unprepared close checks Done inside the acquired lock, even if an earlier preflight passed while it was contended. A still-bound prepared native close keeps its saved checks. The default (or `"every-lane"`) keeps the per-lane hook behavior; `thread: "none"` never invokes a thread hook.

The lead owns a shared thread's title and completion state; launch footers tell lanes not to rename or archive it when their own part finishes. Grouping changes only the existing hook decision, not the title or archive flag. Park and abandon never run the Done hook. Hooks remain external, best-effort effects: a crash after the close, or a failing hook, requires the lead to reconcile it. A member reopened after the close commit, or a new lane registered after the snapshot, is new work, not part of that completed election.

Closes a lane now. Refuses (exit 2) unless every `Done =` signal reads back live or a still-bound native close already recorded the checks. Close and watch use the lane's delivery lock, so a `dori tell` or `dori pause` either finishes first or sees the resulting lane state. A delivery lock held beyond 30 seconds prints `HELD <key> a message to the lane is in flight (<holder>)` (manual close, exit 2) or `LANE_HELD ...; retried next tick` (watch).

On success a closed lane also gives back what dori opened for it: its tab, or, for a lane placed as a split, only its session. A workspace dori created is closed once its last open member is gone. A workspace dori did not create, the lead session and `ignorePanes` are never closed.

Native closes refuse a confirmed working or blocked main, including approval waits, with `HELD` / `LANE_HELD`. When close preparation can bind the native process, the existing intent records its exact PID, kernel `startTicks` and `bootId`; cleanup then requires both pane absence and that process incarnation's exit. This applies to first-run and reopened lanes on herdr and hc. HC prepared-close recovery requires complete observed foreground arguments: a name alone or malformed argv stays held even after the saved native process exits. A surviving process or failed/invalid read after preparation stays held; a later watch tick can settle after exit without closing the missing pane again. An interrupted close can also resume after that process exits when a fresh probe confirms only a bare shell remains; another native writer or a shell script stays held. Wall-clock shifts cannot release this fence. A reused PID from a different kernel incarnation is not signalled. An older prepared intent can acquire missing proof only from its still-live bound pane. An initial legacy close with no prepared proof retains its existing behavior when native identity is unknown, including a main that already shut down; it gains no unknown-state safety guarantee.

These are living-work safety guards, not a full quiescence barrier. They do not guarantee safety for an unknown initial lane or completion of owned async jobs, queued input or services; that broader policy needs native read-only, explicit-unknown and quiescence APIs. Holding every unknown initial close, or retaining PID/boot/start evidence in native retirement records, are separate follow-up policies, not part of this change. `native-omp.patch` and `native-omp.lock` are unchanged.

### `dori lesson add <key> --rule TEXT --evidence PATH [--cwd DIR]` / `lesson add --global --rule TEXT --evidence REF` / `lesson list [--cwd DIR]` / `lesson mark <id> --outcome ...`
A lesson is one rule learned in a lane, tied to the evidence that taught it and to the lane's repo (its `cwd`, resolved to a real path). A `--global` lesson is the lead's standing rule for every lane, whatever its repo: it has no `cwd` and is recorded as `lane: "lead"`. Since it reaches every future brief, it is the lead's: `--global` with a lane key is refused and writes nothing. So are `--global` and `lesson mark` on a global lesson when run from a pane that a registered open lane owns (your own session, from `HC_TERMINAL_ID`, else `HERDR_PANE_ID`, found as `claim-done` finds its lane); repo lessons stay markable from lanes. The pane check is a convenience check that stops a lane from adding or reviving a global lesson by accident or on routine instruction. It is not a security boundary: it reads only the session variables (`HC_TERMINAL_ID` first, then `HERDR_PANE_ID`), so unsetting them gets past it, and anything that can write files can append to `lessons.jsonl` directly. `dori launch` puts the newest `pending` or `helped` lessons for the new lane above its brief: up to 12 global ones under "Lessons for every lane", then up to 8 for its `cwd` under "Lessons for this repo". Each kind has its own cap, so global rules never push repo lessons out. A global cap only bounds runaway growth: a standing rule the owner gave must not disappear because newer ones arrived, so the cap sits well above the orders a real home holds. A lesson a cap still keeps out is returned in `omitted` and printed on stderr as `LESSON_OMITTED <id> (global) <rule>` for a global lesson or `LESSON_OMITTED <id> (<canonical-cwd>) <rule>` for a repo lesson, beside the launch warnings. `lesson list --cwd DIR` shows the global lessons too. `mark` records whether a lesson `helped`, had `no-effect`, was `harmful`, or is now `encoded` in a test, lint or doc; only `pending` and `helped` reach new briefs. Lessons live in `<stateDir>/lessons.jsonl`, one record per change: a mark appends, it never rewrites history. A rule is one line of at most 400 characters. A damaged line (not JSON, an unknown field, a malformed field, or a change to a lesson's fixed fields) is skipped and named: `lesson list` and `launch` print `LESSON_WARNING <path>:<line>: <reason>` on stderr and go on with the other lessons. The reason names the field for a malformed, unknown or changed field; a line that is not JSON, or not a JSON object, has no field to name and is reported as such. Each record starts on its own line, so a write cut off halfway damages only its own line.

`dori close <key> --lesson TEXT [--evidence PATH]` adds a lesson as part of the close (evidence defaults to the `Done =` line). It never blocks the close: a failure prints `LESSON_WARNING`.

### `dori worklog add <title> --source REF [--thread REF]` / `next <id> <text>` / `note <id> <text>` / `close <id> --result TEXT` / `list [--open]`
Optional `--thread REF` links the owner request to its work thread in the JSON record, rendered Markdown and boot output. The reference must be nonempty, whitespace-free and not `none`; old entries without it remain readable. Closing a worklog item does not close its lanes or its thread.

The lead's record of owner requests, so an open request survives a restart, a compaction or a handoff. `add` records a request when it arrives, with its source (`slack:<channel>/<ts>` or any reference to the message) and prints the item with its 8-hex-digit id. `next` replaces the item's next step, `note` adds a dated note (a decision, who owns it), `close` records the result and ends the item; a closed or unknown item is refused. Each text is one line, without control characters (C0, DEL, C1) or the Unicode line and paragraph separators. `list` prints the items as JSON (`--open` only the open ones), oldest first.

The record is `<stateDir>/worklog.jsonl`, one append per change, so the lead and a lane can write at the same time without losing one; a write cut off halfway damages only its own line, which every reader skips quietly as a normal result of the design (a line that does not parse but begins like a record, `{"op":"`). Any other bad line is real damage: `list` names it as `WORKLOG_WARNING <path>:<line>: <reason>` and skips it. If two writers close the same item at once, the first close in the record wins and a later `close` is a no-op; a `next` or `note` after the close lost the same race: it is skipped and `list` still names it as a `WORKLOG_WARNING`. After every change `<stateDir>/worklog.md` is rendered from the whole record (temp file and rename) for the lead to read: one heading per item with Source, Opened, Next, Notes and, once closed, Closed and Result, open items first. A render that raced another writer's append renders again, so the file always ends up holding every item. Edit through the command, not the file: a `worklog.md` that the command did not write (no marker on its first line) is never replaced (the marker is checked before the append and again right before the rename, and a publish that finds it gone is skipped), and every change is refused until it is moved aside.

`dori boot` prints `WORKLOG open=<n>` and one `OPEN <id> "<title>" source="<ref>" next="<next step>"` line per open item, so the lead continues each from its Next line. A damaged line (not a torn write, a duplicate close, or a `next`/`note` after a close) is `WORKLOG damaged <path>:<line>: <reason>` and makes the boot incomplete. A `next` or `note` after a close prints as `WORKLOG warning <path>:<line>: <reason>` and does not fail the boot.

### `dori decision ask <question> --source REF ...` / `posted` / `answer` / `choose` / `withdraw` / `match` / `list` / `digest`
The lead's record of product choices put to the owner, and of the lead's own routine choices, so a pending question is asked once, re-posted from the record rather than from memory, and its answer is bound to the right question and to who gave it. Successful mutating commands print the resulting decision as JSON; the read commands have the formats described below.

Each decision has a `kind`. `owner` is the default, and every decision recorded without a kind (including every record written before kinds existed) reads as `owner`: only the owner's answer settles it. `routine` is a reversible choice inside the work's original scope and goal, between options already named: the owner may still answer it, and the lead may instead choose one of its numbered options with `choose`. Cost or spending, permissions or access, commitments to anyone outside, irreversible work, a change of scope or goal, and open questions are `owner`. The record never guesses a kind from the question's words; the lead states it when asking. No answer or choice in this record is a permission grant: a native execution approval is answered only at its own prompt, and nothing here reads or changes one.

The command records the provenance the caller supplies; it does not fetch that message or authenticate its author. `authority` names the recorded answer path, not a new permission grant.

- `ask <question> --source REF [--lane K] [--thread REF] [--kind owner|routine] [--option TEXT]... [--recommend N] [--worklog ID] [--message REF]` records a question with an 8-hex-digit id. `--option` may repeat up to 9 times; options are numbered 1..n in the order given. `--kind routine` needs at least two options and a thread (given, or the lane's), so an open question or one without the work's thread stays the owner's; any other `--kind` than `owner` or `routine` is refused. Any value flag of `dori decision` (`--source`, `--lane`, `--thread`, `--kind`, `--option`, `--recommend`, `--worklog`, `--message`, `--reason`) with no value, at the end of the line or followed by another flag, is refused with `<flag> needs a value` and nothing is written; a value that starts with `--` is given as `--option=--text`. `--recommend N` marks one option and is refused without options or outside 1..n. `--lane` must be a registered lane (open or closed); without `--thread` the lane's thread is stored, and `--thread none` stores no thread. `--worklog` links an open worklog item and is refused for an unknown or closed one. `--message` is where the question was posted (for example `discord:<channel>/<message-id>`).
- `posted <id> --message REF` records or replaces the posted message of an open decision.
- `answer <id> <answer> --source REF` records the owner's answer and the owner message it came from. When the decision has options and the answer is a bare number, it must be one of them and is recorded as `option: N` with the text; a number outside 1..n is refused and nothing is written. Any other text is recorded as free text with no option: a match is never guessed. When the decision links an open worklog item, a note `decision <id> answered: <answer>` is added to it. If that note would exceed 1000 characters, it records `decision <id> answered (see decisions.jsonl)` instead; the full answer stays in the decision ledger. A failed note prints `DECISION_WARNING <reason>` on stderr and keeps the answer. The decision reads `authority: "owner"`.
- `choose <id> <N> --reason TEXT --source REF --thread REF` records the lead's own choice of option N of an open `routine` decision. First post the choice and its reason in the decision's original thread through the usual messaging; `--source` is that posted message and `--thread` must be exactly the decision's thread. The decision then reads `authority: "lead"`, `option: N`, `answer` as that option's text, `reason`, and `answerSource` as the posted message; its question `source` and `thread` stay as asked. An `owner` decision, anything other than exactly one bare option number in 1..n (free text, a number outside the options, two numbers), a missing or different `--thread`, or other than exactly one `--reason` is refused and nothing is written. A linked open worklog item gets the note `decision <id> chosen by the lead: <option>`. `choose` sends no message, does not forward the choice to a lane, and grants no permission.
- `withdraw <id> --reason TEXT` ends a decision that is no longer needed because it became moot. It records no choice: it is not a way for the lead to decide an `owner` decision.
- `match <message-ref>` prints the open decision posted as exactly that message and exits 0; with none it prints nothing and exits 1. This binds a reply: read the replied-to message id of the inbound reply and run `match` before reading the reply as an answer. A reply to any other message is an ordinary message. Only one open decision may be posted as a given message, so `ask --message` and `posted` refuse a message already bound to another open decision.
  - The reference is what a reply names, written the same way for `--message` and `match` (for example `<messenger>:<chat>/<id>`): on Discord use the physical channel and `ref=` on the owner `INBOUND` line, not the supplemental snapshot or its author; on Telegram use `reply=`. A Slack reply names only its thread root (the `<thread>` field of `INBOUND slack`), not a message inside the thread. So a question posted in a Slack thread is recorded with the thread root as `--message` (the question's own ts when it starts the thread; the ts `SENT` prints for a message posted inside a thread never matches a reply): one open decision per Slack thread, and every owner message in that thread matches it, so read the reply before recording it as the answer.
- `list [--open]` prints the decisions as JSON, oldest first. `digest` prints one line per open decision for a status message: `<id> <age>h lane=<k|-> kind=<owner|routine> <question> | 1) <option> | 2) <option> (recommended)`. `match`, `list` and `digest` send damage and warnings to stderr as `DECISION_WARNING ...`.

An unknown decision, or one already answered or withdrawn, is refused with a one-line error. Each text is one line without control characters (C0, DEL, C1) or the Unicode line and paragraph separators, and a lane, thread or message reference has no spaces. A lane launched without a thread (recorded as `none`) gives no thread.

The record is `<stateDir>/decisions.jsonl`, one append per change (`ask`, `posted`, `answer`, `choose`, `withdraw`), with no rendered view. An `ask` records `kind` only when one was given; a `choose` record holds the option number, reason, source and thread, never answer text. The same rules hold when the record is read, so a hand-written or raced line cannot get past them: a `routine` ask without two options or a thread, a `choose` for an `owner` decision, for another thread or for an option the decision does not have, or one without an option number, is damage and settles nothing, even when it comes after the decision was settled. A `choose` counts as an answer in the races below. A record with `kind` or `choose` is unknown to an older `dori`, which names it as damage. As in the worklog, a write cut off halfway damages only its own line and is skipped quietly, any other bad line or unknown field is damage, and every write is read back. Each record carries its own random nonce `n` (8 hex digits), and a command judges its readback by that nonce, never by matching text or time, so two identical changes in the same millisecond are still told apart. If two writers resolve the same decision at once, the first `answer`, `choose` or `withdraw` in the record wins; a later `answer`, `choose`, `withdraw` or `posted` is ignored and named as a warning, and the losing command fails with a one-line error saying so (a losing `answer` or `choose` writes no worklog note). Message binding races the same way: the first `ask --message` or `posted` in the record binds a message among open decisions, and a later one naming a message another open decision holds does not bind it and is named as a warning. A losing `posted` changes nothing; a losing `ask` still records the decision, without the message, and its error names the holder and says to bind it with `decision posted` once the message is free. A `posted` replaced by a later `posted` before its readback reports that it was replaced. A resolved decision frees its message.

`dori boot` prints `DECISIONS open=<n>` and one `DECIDE <id> age=<h>h lane=<k|-> thread=<ref|-> "<question>"` line per open decision after the `WORKLOG` lines. A damaged line is `DECISIONS damaged <path>:<line>: <reason>` and an unreadable record `DECISIONS unreadable <path>`; both make the boot incomplete. A lost race (a late change after a resolution, or a message binding another open decision already held) is `DECISIONS warning ...` and does not fail it. Without `decisions.jsonl`, boot prints nothing about decisions.

Nothing is decided automatically: there are no defaults and silence is never an answer; a recommendation is not a choice, and a `routine` decision stays open until the owner answers or the lead records a `choose`. The command does not forward an answer or choice to a lane; the lead does that itself (with `dori tell` once available, or the existing session messaging rules). Owner requests stay in `dori worklog`; harness `backlog --decision` is for harness items not yet started, and a lane's `report --kind question` only marks that lane blocked.

### `dori pause <key> [--note TEXT]` / `dori resume <key> [--note TEXT]`
`pause` is for when the owner said wait. It works on a `working` or `not-done` lane. It sends `/goal pause`, then confirms the current OMP session's recorded goal is paused or absent before marking the lane paused and sending Escape to an active turn. A completed/dropped goal requires the corresponding OMP no-goal screen response as corroboration. Missing/stale state, an open approval, or an unconfirmed send leaves the lane unchanged with `PAUSE_UNVERIFIED`, exit 3. Pausing the goal first prevents Escape from triggering a continuation. The whole pause holds the lane's delivery lock (see `dori tell`), so no tell starts a turn after its Escape; if a tell holds the lock for 30 seconds, the pause sends nothing and prints `PAUSE_UNVERIFIED <key> a message to the lane is in flight (delivery lock: <holder>); lane left <status>`, exit 3.

A paused lane is skipped by `freshness`: no nudge, no post. Only `dori resume` ends a pause, on the owner's word. Activity never does, because a paused lane can still be woken by a background result, a queued message or a turn after Escape. If its pane reads `working` on two ticks in a row, `freshness` prints `WORKING-WHILE-PAUSED` once per working stretch (again after it goes idle and is woken, or after a new pause), so the lead can ask the owner, and the lane stays paused.

`resume` sends `/goal resume` and confirms the trusted OMP goal state is active, then restores the lane's `pausedFrom` status and resets quiet time so a long pause does not become an instant nudge. Missing/stale state, an approval hold or an unconfirmed send gives `RESUME_UNVERIFIED`, exit 3.

Both print `PAUSED` / `RESUMED` and exit 0 on success. A lane in any other state is refused (`NOT_PAUSED` / `NOT_RESUMED`, exit 2), and a second `pause` is a no-op. A lane claimed, objected to or closed while the goal command ran is left as that writer put it (`LANE_CHANGED`, exit 3); the goal command itself was confirmed, so check the lane before retrying. `claim-done` and `object-done` on a paused lane move it out of `paused` in the registry while its goal stays paused.

### `dori park <key> --note TEXT [--resume-when TEXT]` / `dori reopen <key> [--note TEXT]` / `dori holds [--thread REF]`

`park` pauses an exact bound OMP session and closes only its pane; `close <key> --abandon --reason TEXT` explicitly ends unfinished work. Neither claims Done or removes worktrees. `holds` lists pauses and parked or interrupted park intents without changing anything. Reopen is explicit and reuses the recorded session. See [pause, park and abandon](sessions.md#pause-park-and-abandon) for identity, pending Discord work and recovery rules.

### `dori tell <key> --text TEXT`
Sends the lead's message to a registered lane's session once through `sendVerified`, the same path `claim-done`, `object-done`, `pause` and the freshness nudge use, and prints one line:

| Line | Exit | Meaning |
|---|---|---|
| `TOLD <key> delivery=confirmed` | 0 | the agent's status moved to working after the send |
| `TELL_UNCONFIRMED <key> delivery=unconfirmed: ...; do not resend` | 3 | the text may be in the session, but no move to working was seen. An agent that was already working gets it as queued input and always lands here. So does herdr's typed fallback when the text was typed but its Enter failed (stderr says `text typed but Enter failed`): read the pane, and if the text still sits in the input, press Enter only |
| `TELL_FAILED <key> delivery=failed: <why>; nothing was sent` | 2 | no running agent (a shell, a suspended or stopped agent), an open approval, an unreadable status, on hc an agent that is `blocked` or in `error` or whose status changed just before the send, a paused lane, a lane with no session, or text containing a backtick or `$(`. When the runtime refused the delivery, `<why>` ends with `(status now: <status>)` read after the refusal (the paused, sessionless and unsafe-text refusals read nothing), so a blocked agent waiting on a question is told apart from a shell (`no agent`). `idle` or `working` there means a shell in front of a suspended agent, an open approval or a failed probe: read the pane before trying again |

No `[LEAD]` prefix is added. Like every `--text`, leading and trailing whitespace is trimmed. The runtime's delivery shapes the rest: hc sends the text as it is, while herdr's typed fallback (used for agents herdr did not start) joins lines into one, replacing each line break and the indentation around it with ` / `, so a multi-line message arrives as one line there. A paused lane is refused because a message would start a turn the owner asked to hold; `dori resume` it first. tell reads the lane again under the lane's delivery lock (`<stateDir>/lanes/<key>.deliver.lock`), which `dori pause` holds from its `/goal pause` through its registry change and Escape: a tell either lands before a pause, whose Escape then stops the turn it started, or finds the lane paused and sends nothing. If the lock stays held for 30 seconds, tell sends nothing (`TELL_FAILED ... a pause or another tell holds the lane's delivery lock (<holder>)`); a holder that died is taken over, but a live one on this host keeps the lock however long its pane round trips take (30 seconds is how long the other side waits, not how long a holder may hold). `dori close` and the watch's auto-close take the same lock to mark a lane closed, so a lane closed meanwhile is refused the same way and a close never lands in the middle of a send. An unknown or closed key and a missing `--text` exit 1. Nothing is written to the registry or the lane's journal.

### `dori watch`
Runs forever. Every 30 seconds it prints each new claim once (`LANE_DONE_CLAIMED`). Claims older than `closeAfterMin` are settled: unpushed or uncommitted work and failing signals turn into objections (`LANE_NOT_DONE`); otherwise the lane is closed (`LANE_CLOSED`). A claim that is objected to, claimed again, paused or closed while these checks run is left as the other writer put it (`LANE_CHANGED`). Verifying and closing hold the lane's delivery lock (see `dori tell`); while a tell or pause holds it past 30 seconds, the claim is left as it is with `LANE_HELD <key> ...; retried next tick`. The deadline lives in the registry, so a restart picks up where it left off.

### `dori freshness [--loop MIN]`
For working lanes that have gone quiet: a nudge in the pane after `nudgeAfterMin`, then the lane's last `[REPORT]` line posted to its thread after `postAfterMin`, with home paths and pane ids scrubbed. Each happens once per silence. The line is posted only once it is still the last `[REPORT]` line on the next tick (`PENDING-REPORT` the first time) and differs from the line posted last time (`STALE-REPORT` otherwise). A post whose `hooks.threadReply` command exits non-zero is not recorded as posted: it prints `POST-FAILED <key> thread hook failed (exit <code>)`, without copying private hook stderr, and is sent again on the next tick; the same failure for the same line is printed once, not on every retry. A `[REPORT]` line counts when it starts the row or is a whole quoted element of an argv array, the shape lanes send it in (`["herdr", "pane", "run", "<lead pane>", "[REPORT] key | kind | text"]`, or `["hc", "send", "<lead terminal>", "--", "[REPORT] key | kind | text"]` on hc). Prose that quotes the grammar mid-sentence, and a report whose text is one unfilled placeholder, are not reports. A held-back outcome is printed once per change, not on every tick. A nudge reports its delivery as `delivered` (the agent status moved to working) or `unconfirmed`.

A lane with a `reports.jsonl` journal is read from the journal first. Its last report skips the two-tick `PENDING-REPORT` wait, since it cannot scroll off, and is posted once the thread has had no update for `postAfterMin`, so a lane that reports often still has its latest report posted, at most once per `postAfterMin`. Its time counts as the lane last being heard from, so a fresh report suppresses the nudge. A `blocker`, `question`, `halted` or `done` lane is not nudged, but its report is still posted. A `stalled` lane is neither nudged nor posted: it stopped on a failed compaction or at an idle prompt, so a typed nudge cannot restart it and a person has to look. `STALLED` is printed once per stall for the monitor (see the filter in `setup.md`), and `Working` on the screen returns the lane to running, after which nudges and posts resume. A `jsonl-v1` lane never falls back to scraping the screen. `launch` starts its journal with a `running` activity record, which is not a report, so a lane with no report of its own is `NO-REPORT` and is still watched for a stall; a `jsonl-v1` lane with no journal at all is `NO-REPORT` and is not watched. The screen is still read for activity: a compaction failure with no `Working` line below it, or an idle prompt with no `Working` line and no report for `nudgeAfterMin`, marks the lane `stalled` and prints `STALLED` once; `Working` on the screen moves it back to running. A journal that does not parse skips its lane and prints `JOURNAL-ERROR` with the file and line, once per error; the other lanes are still swept. Adopted lanes ignore the journal and keep the screen path. On the screen, a report is a line that starts with `[REPORT]` (after indentation) or the last quoted element of an argv row such as `["herdr", "pane", "run", "lead:p1", "[REPORT] ..."]`, optionally inside one spawn call. Prose, an instruction or a prompt that quotes the grammar mid-sentence is dropped.

#### Opt-in nudge and posting policy

Defaults preserve the behavior above. Set `freshness` in the config to choose the quieter policy:

```json
"freshness": { "nudge": "idle-only", "autoPostKinds": ["milestone"], "postRaw": false }
```

- `nudge: "idle-only"` requires a trusted runtime probe to report a live idle agent without a shell or approval prompt before safe delivery. hc also conditions delivery on idle; herdr has no atomic status-and-send operation, so this is a live pre-send check, not an atomic guarantee. Working, blocked, unknown and missing agents are not nudged. An unknown status is not evidence of idleness. A failed safe-delivery attempt emits `NUDGE-FAILED` once per silence stretch and retries on later ticks; it does not consume the nudge. The existing paused-lane, stall, hung-call and ceiling checks still run. `"all"` is the legacy default.
- `autoPostKinds` limits automatic posts; omitted means all five kinds, and `[]` means none. Excluded reports produce one `UNRELAYED` notice to the lead per report/change, not a raw owner message.
- `postRaw: false` posts only a supplied `--owner` summary. A report without one (including adopted screen reports), or a missing reply hook, produces `UNRELAYED`; `true` is the legacy default. New launch footers request the owner summary when this option is set; an existing lane needs an updated brief or the lead's manual relay. Add `UNRELAYED` and `NUDGE-FAILED` to a freshness monitor's filter. A summary is preferred whenever present.
- `relayed` receipts suppress the acknowledged journal report across restarts. A changed kind, text or summary remains eligible; an identical line and summary with only a newer timestamp retains the legacy no-repeat behavior. Legacy screen reports retain their two-tick and last-line checks. A failed reply hook never creates a receipt.

Run one freshness monitor per state directory. The sweep rechecks receipts before invoking the hook and never overwrites a receipt recorded while the hook runs. A manual send can still race the hook after that check. A receipt records confirmed delivery, not an atomic transaction with an external messenger: a crash after delivery but before recording may still require the lead to reconcile the message.

#### Supervision
For launched (`jsonl-v1`) lanes whose `reports.jsonl` journal exists, each `freshness` tick also checks the items below. An adopted lane is not supervised: it has no ceilings and no hung-call check, even if a journal exists for its key.
- **Ceilings.** `wallMinutes` since the lane opened, and `tokens` and `costUsd` from `supervision.usageArgv`. Reaching one appends a `blocker` report and prints `BLOCKED`. The lane is never killed, closed or sent anything; it waits for the lead, and raising a ceiling alone does not resume it. Limits come from `supervision.defaults`, then `supervision.lanes.<key>`, then `launch --wall-minutes N|none --token-limit N|none --cost-limit N|none`, and are saved on the lane. `null` (`none`) disables one. A malformed `supervision` entry (a ceiling that is not a nonnegative number or `null`, a ceiling or setting name that does not exist, such as `toknes`, a `lanes` entry that is not an object, an argv or path list that is not strings) stops every command with `invalid supervision <name>`, so a typo never turns a ceiling off.
- **Hung calls.** A `Working` or `Running` timer on the screen that keeps growing from the same start for `hungAfterMinutes`, with no new report, checkpoint or file change for `staleAfterMinutes`, marks the lane stalled (`STALLED`). File changes are git's changed-file list in the lane's `cwd` (`gitActivity`), leaving out `node_modules` and paths outside `cwd`, plus `activityPaths` and `launch --activity-path FILE`; directories are not walked.
- **Usage.** `supervision.usageArgv` is an argv template (`{key}`, `{session}`, `{cwd}`) that prints `{"tokens": N, "costUsd": N}` cumulative totals. Missing or malformed values are unknown, never zero, and a ceiling that cannot be checked prints `WARNING` once. With `usageArgv` set, each reading is appended to the lane's `cost.jsonl`; without it, sweeps record nothing.

Each alert prints once per change. `close` takes one more usage reading, prints `COST <key> tokens=... costUsd=...`, and, when either is known, runs `supervision.recordCostArgv` (`{key}`, `{session}`, `{tokens}`, `{costUsd}`, `{at}`, and `{closeKey}`, `<key>@<openedAt>`, the same on every attempt; unknown values are the literal `null`). Once the hook succeeds the reading is marked final in `cost.jsonl`, and a later close of the same lane returns it without running the hook again. If that hook fails, close prints `COST <key> not recorded: <reason>` and still closes the lane. A supervision step that fails (an unreadable `supervision.json` or checkpoint journal) prints `SUPERVISION-ERROR <key> <reason>` once per reason; that lane's reports are still read and posted, and the other lanes are still checked. Both hooks run without a shell and time out after 10 seconds. Run one `freshness` sweeper for all lanes: each tick covers every open lane, so a second sweeper would repeat nudges, thread posts and supervision alerts.

### `dori dead-panes [--loop MIN]`
After all watched runtime/group listings succeed, the loop forgets screen tails and unknown counts for panes no longer watched, and retains alert deduplication keys only for currently watched panes in the current hour. A failed or malformed listing preserves the prior state: runtime list adapters reject missing/non-array results and malformed rows rather than treating them as an empty snapshot. A returning pane starts a fresh two-screen/three-unknown-tick observation; a change of hour (including a backward clock step) starts a fresh hourly deduplication window.

Prints `DEAD_PANE <id>` once per hour for a pane with no running agent status whose last lines match `deadPanePatterns` on two ticks in a row with the same text. A pane the runtime reports as idle, working, blocked or done (on hc: the agent's own report, which can also be error) is never dead. A pane that is neither is unrecognised; three unrecognised ticks in a row print `UNRECOGNISED_PANE <id> ...` once (list non-agent panes in `ignorePanes`).

### `dori guard [--loop MIN]`
Prints `HOST_GUARD ALERT <reasons>` when load, free memory, free disk or the pane count crosses its threshold, and `HOST_GUARD CLEAR` when it recovers. It also prints `COMPUTE_READY` / `COMPUTE_BUSY` as load crosses `loadOk`. Only changes are printed.

### `dori can-launch`
Prints `CAN_LAUNCH` and exits 0 when the host has room for another lane. Otherwise it prints `HOLD <reasons>` and exits 4. The reasons come from the guard's memory, disk and pane-count thresholds. CPU load alone never holds a launch, because it moves too fast to plan around.

### Discord REST test endpoint
With `DORI_DISCORD_API_BASE` unset or empty, Discord REST requests use `https://discord.com/api/v10`. For an isolated test server, set it to an HTTP URL on `127.0.0.1`, `localhost` or `[::1]`, optionally with a path prefix; trailing slashes are removed. Credentials, query strings and fragments are refused without echoing the configured value. The local server receives the normal Bot authorization header, so use a synthetic token for tests. This overrides REST only, not Gateway or attachment/CDN URLs.

### `dori send <slack|telegram|discord> --to TARGET (--text TEXT | --text-file PATH) [--thread ID] [--edit ID] [--reply ID]`
The body comes from `--text`, or from `--text-file PATH` read as UTF-8 (`-` reads standard input), so a long report or a body with quotes never passes through a shell string. Choose one; both, an unreadable file (the error names its code, such as `ENOENT`) or a body that is empty after trimming are refused before any request. A file body is trimmed like `--text` and gets the same `$(` refusal.

Posts a message, or edits one with `--edit`. Tokens come from `DORI_SLACK_TOKEN`, or when that is unset or empty from the file `DORI_SLACK_TOKEN_FILE` names (plus `DORI_SLACK_COOKIE` for a user token). The file must be a regular file you own and owner-only (`chmod 600`), checked and read through one open descriptor; a file open to group or others, owned by someone else, not a regular file (a FIFO never blocks the read), missing or empty is refused. Windows has no mode bits or uid to check, so there the file's ACL is the owner's to set, and `dori boot` prints `SLACK token-file: the token file's NTFS ACL is not checked on Windows; ...` as a reminder. Other tokens come from `DORI_TELEGRAM_TOKEN` or `DORI_DISCORD_TOKEN`. Text containing `$(` is refused, since it can only come from a shell string.

Messenger writes never automatically retry HTTP 408/5xx, a lost response, or an unreadable success acknowledgement. The CLI exits nonzero on uncertain delivery; library callers receive `MessengerError` with `code="DELIVERY_UNCERTAIN"` and `outcome="uncertain"`. This is not a confirmed rejection or a successful send. Keep the original command/target and any confirmed IDs: inspect that exact remote conversation, thread or file before deciding whether another write is safe. Do not repeat the whole command or generate a new request identity merely because no receipt arrived. Discord and Telegram partial-send failures name the earlier confirmed message IDs and stop before later parts. A Discord `--reply` that receives a parseable success object without a valid message ID still sends each remaining part once, retains its known IDs, and leaves the exact owner request unsettled. A later part's rejection does not resolve the earlier uncertainty.

If Slack confirms a post but local thread tracking fails, the error instead carries `outcome="confirmed"`, `code="DELIVERY_CONFIRMED_LOCAL_ERROR"` and the original channel/message receipt; repair tracking rather than reposting. No automatic reconciliation or durable outbox is implied. Ordinary 4xx/API rejections remain `outcome="rejected"`. Automatic HTTP 429 retries honor `Retry-After` within the existing 60-second per-wait budget. A longer delay surfaces HTTP 429 without waiting or retrying early. GET and explicitly recognized read-only Slack/Telegram RPCs retain bounded 5xx backoff, while unknown RPC methods are conservatively treated as writes. An uncertain result when Discord opens the owner DM (`POST /users/@me/channels`) stops scope-all startup, REST refresh, or Gateway backfill without automatically repeating the write. Inspect the target before rerunning discovery; ordinary history GET retries are unchanged.

`send telegram` splits plain text into consecutive messages of at most 4096 UTF-16 code units. It prefers a newline, then a space, in the back half of the window, and otherwise cuts at a whole Unicode character. Concatenating the parts gives the exact original text, including whitespace and non-BMP characters. On success, `SENT` names the last part. An API failure stops the remaining parts; earlier successful sends remain. No message-ID journal or multi-message editing is maintained.

`--edit` always updates one existing message in place. Input over 4096 UTF-16 code units fails with an instruction to shorten the text or send without `--edit`, before any API request or mutation. It never edits a prefix and posts the remainder. The library's `rich=true` send path retains one unsplit HTML request, leaving Telegram to validate markup and its rendered-length limit. Rich edits use the same conservative preflight bound on the complete raw HTML, including tags and entities; markup over that bound is rejected even if its rendered text would fit. Short rich sends and edits keep their existing HTML behavior. HTML-aware splitting and multi-message edits are not implemented.

On Discord, `--to` accepts an exact channel ID. With `DORI_DISCORD_GUILD_ID` set, it also accepts a unique channel name, with or without `#` (`--to chat` or `--to '#chat'`). Missing or ambiguous names fail before sending. `--thread ID` needs no `--to` and selects the thread for both sending and `--edit`; an edit still updates one message without printing a `SENT` line. New messages disable mentions. Forum and media channels hold posts rather than messages, so direct sends point to `dori thread discord create`.

`send discord` splits text over 2000 UTF-16 code units into consecutive messages. It prefers a blank line, then a newline, then a space in the back half of the window, and otherwise cuts at a whole Unicode character. Code blocks follow Discord's rendering: runs of three or more backticks pair up in order wherever they sit, so a one-line block or a closer with text after it on its line closes the block. A block that a cut leaves open is closed with three backticks at the end of that part and reopened with three backticks and its language at the start of the next, so every part renders on its own; a language that is not 1 to 32 letters, digits or `_+-.#` reopens without one. When the cut falls just before the block's own closer, that closer ends the part instead of an empty block opening the next; a part never ends on a block's opening line, and a cut never falls inside a run of backticks. Parts that would hold only whitespace are dropped, since Discord refuses empty messages. Apart from those markers and dropped whitespace, the parts join back to the text. `SENT` lists every message ID in order. A failed part stops the rest; once a part is posted, any later failure, a transport error included, ends with `(part N of M; already posted: <ids>)`, and the posted parts stay.

`--reply MESSAGE_ID` makes the first part a reply to that message in the target channel or thread, without pinging its author. The reference is bound to that exact physical channel (a thread has its own channel ID). Discord must accept the original message reference atomically: a deleted, unavailable or other-channel target fails instead of falling back to an unlinked post, and no later part is sent after that rejection. It is checked before any request: an empty or non-ID value, or `--reply` with `--edit`, is refused. Slack and Telegram refuse `--reply` instead of posting without it. `--edit` is never split: Discord text over 2000 code units is refused before any request.

The Discord owed-answer gate requires `--reply` to name the original owner message in the exact destination channel or thread. After every part succeeds, `owes/sent.jsonl` records that request ID, a delivery ID and the complete ordered remote-message ID list. A partial or uncertain send, an edit, typing, a reaction alone, or a successful unlinked post never settles the request. Older channel/time-only receipts are ignored rather than guessed onto a request. The existing exact-message read mark, stale-owe limit and bounded continuations still apply. API acceptance is not proof that the owner read the answer; do not automatically resend an uncertain delivery.

`send discord --render-tables` opts into aligned, monospaced pipe tables before the existing delivery path. The default remains the original text. Padding uses Unicode display width for CJK and emoji, preserves source escapes and inline code, and leaves existing fenced code and non-table text unchanged. Formatting is limited to 80 display columns (including indentation) and a 64 KiB UTF-8 budget for the complete transformed message, checked before padding is allocated. An oversized table/message or ambiguous row/code syntax keeps the original message; nothing is truncated. Indented code blocks and unsupported nested fence syntax are not reinterpreted.

The flag applies to Discord sends and edits only; Slack and Telegram sends reject it. Rendered sends use the same 2000-code-unit splitting, first-part reply, disabled mentions and partial-send receipts described above. Rendering can add split parts. For `--edit`, the rendered text must fit one message: overflow is refused before any request, never converted into a new post. The formatter does not turn on automatically for SDK calls, thread starters or other commands.

### `dori thread discord create --to CHANNEL --title T [--text T] [--tag NAME]... [--message ID]`
Creates a public thread in a text channel, or a post in a forum/media channel. `--to` uses the same ID/name lookup as Discord sends. A forum post uses `--text`, or the complete title when text is omitted, as its starter message. In a text channel, optional `--text` is sent inside the newly created thread. Authored whitespace is retained in titles and starter text; titles are limited to 100 characters. Starter messages disable mentions. Text over 2000 code units is split as `send discord` splits it: a forum post's starter holds the first part and the rest follow in the post, and ` mid=` names the first message.

`--message ID` opens the thread on that existing message of the text channel (for example the owner's request) instead of a new thread without a starter; optional `--text` is then sent inside it. An invalid ID or `--tag` with `--message` is refused before any request; a forum or media channel is refused after its lookup.

Repeat `--tag NAME` to apply forum tags by name or ID. An unknown tag reports the forum's known tag names; tags on a text-channel thread are rejected. Success prints the API's `THREAD <thread-id>`, with ` mid=<message-id>` when the API returns a starter message ID or an optional text-channel starter is sent. Thread creation and the messages sent after it (a text-channel or `--message` thread's text, a forum post's further parts) are separate API operations; if one of those sends fails, the created thread and the parts already posted remain.

### `dori thread discord set <thread-id> [--title T] [--tag NAME]... [--archive|--unarchive]`
Renames a thread, replaces a forum post's complete applied-tag list, archives it or reopens it. Tag names/IDs resolve against the parent forum; unknown tags include its known tag names in the error. Supply at least one change and choose at most one of `--archive` and `--unarchive`. Success prints the thread ID returned by the API as `THREAD <thread-id>`.

### `dori thread discord status <thread-id> done|working`
The lead marks a Discord work thread done or working without archiving it. The command reads the live title, adds exactly one U+2705 check-mark prefix followed by a space for `done`, or removes only that prefix for `working`. It preserves the rest of the current title, including owner renames, and never restores an old snapshot. An unchanged title makes no PATCH request. A non-thread, missing title, empty resulting title or title that would exceed 100 UTF-16 code units is refused rather than truncated. Archive and tag fields are never sent; use the explicit `set` command for those operations. API failures produce no success receipt.

`done` refuses while any open lane names `discord:<id>` or the legacy raw id. A registered lane's session is refused for either state, using the same convenience session check as global lessons; this is not a security boundary against a process that changes its environment. New work registered or a title changed concurrently after the live checks is not an atomic transaction with Discord: the lead must reconcile that race. Success prints `THREAD_STATUS <id> <state> changed|unchanged <title>`.

### `dori react discord --to CHANNEL [--thread ID] --message ID [--emoji E] [--remove]`
Adds the bot's own reaction, using the eyes emoji by default. `--to` is a channel ID; `--thread ID` selects a thread instead and needs no `--to`. `--emoji` accepts Unicode or a custom emoji in Discord's `name:id` form, URL-encoded for the API. `--remove` removes only the bot's own reaction. Success prints `REACTED <channel-or-thread-id> +` for add or `REACTED <channel-or-thread-id> -` for remove.

A successful add also records the exact owner-message read mark used by the owed-answer gate. Removing a reaction does not create a mark. A mark alone never settles the request: a complete `send discord --reply MESSAGE_ID` receipt in the same channel or thread is required too.

### `dori channel discord set <channel> --purpose TEXT` / `clear <channel>` / `list`
Records the operator's purpose note for a Discord channel, thread or DM in `<stateDir>/discord-channels.json` (owner-only, replaced whole under a writer lock), so `dori inbound discord --context` can show what a channel is for beside each owner message. `set` looks the channel up first (an ID, or a unique name with `DORI_DISCORD_GUILD_ID` as `send discord --to` takes it), records its name with the purpose and prints `PURPOSE <id> "<purpose>"`. The purpose is one line of 1 to 500 UTF-16 code units after trimming, without control, line-separator or bidirectional-override characters, checked before any request; a stored entry outside that form counts as damage. A thread's own purpose is kept apart from its channel's; `--context` shows both. `clear <id>` needs no token or lookup, so a deleted channel's note can still be removed, and prints `PURPOSE_CLEARED <id>` or `PURPOSE_NONE <id>`; a name is looked up first. `list` prints `CHANNEL <id> name="..." purpose="..." updated=<time>` per note. A damaged file is reported and never overwritten.

### `dori presence <slack|discord>`
Keeps the account shown as online until explicitly stopped. Enable one instance per account under the owning OMP session's native `monitor` tool; two writers can compete.
- **Discord:** use your own `DORI_DISCORD_TOKEN` in the child environment. REST inbound polling and message sending do not establish online presence. The Gateway keeper emits `PRESENCE_READY discord event=READY|RESUMED` only after that real dispatch, `PRESENCE_ACK discord seq=<number|->` only for the first actual heartbeat acknowledgement per connection and `PRESENCE_RECONNECT` while reconnecting. Later routine acknowledgements update lifecycle state silently. Authentication/configuration/intent failures exit nonzero with sanitized errors. SIGINT/SIGTERM ends retries, sockets and timers with `PRESENCE_STOPPED discord`; intentional monitor stop means offline. Restart only by explicit choice. See [operational details](../../../docs/releases.md#discord-online-presence).
- **Slack, user token:** it opens one web-client-type socket and tickles it every minute. Slack shows a user active only while such a socket is open, and auto-aways an idle one after about 30 minutes. This retained source feature is outside the first Discord preview's live support scope.

### `dori inbound discord [--loop MINUTES] [--gateway | --wake-lanes]`
Discord owner intake is built into Dori and uses the owner's bot token directly. It needs no Node, agent-messenger CLI, SDK adapter or private helper. Required child environment: `DORI_DISCORD_TOKEN`, `DORI_DISCORD_OWNER_ID`, and channel IDs from `DORI_DISCORD_CHANNEL_ID` or `DORI_DISCORD_CHANNEL_IDS` unless `DORI_DISCORD_SCOPE=all` is selected. IDs are positive decimal snowflake strings, never JavaScript numbers. `DORI_DISCORD_CHANNEL_IDS` adds comma-separated channel or thread IDs; all explicit IDs must be readable. Scope `all` adds readable guild text channels, active threads and the owner DM, skipping discovered 403/404 targets including an unavailable DM. Authentication, rate-limit and server failures still propagate. Threads under a watched channel are watched too, unless `DORI_DISCORD_THREADS=off`. Each watched channel has its own cursor.

`--gateway` delivers owner messages live over a Gateway connection (intents `GUILD_MESSAGES`, `DIRECT_MESSAGES`, privileged `MESSAGE_CONTENT`; no presence update). After every `READY`/`RESUMED`, REST gaps and eligible queued owners are reconciled before newer delivery or filtered checkpoints. Records known before each delivery selection are processed in message-ID order per channel; the late-arrival and recovery boundaries below apply. It ignores `--loop`, including `--loop 0`, and runs until stopped. Intake and presence use separate Gateway sessions with independent lifecycles. See the [Gateway mode notes](../../../docs/releases.md#real-time-gateway-mode).

Active threads under configured parent channels are followed automatically at startup, every tenth REST poll and every Gateway READY/RESUMED. Only Discord thread types 10/11/12 make `parent_id` a thread parent; a text channel's category does not. Explicitly configured threads do not make their parent watched. `DORI_DISCORD_THREADS=on` or unset enables following; `off` keeps only configured IDs without changing scope `all` or adding parent lookups there. Discovered history 403/404 targets are skipped without retrying every unchanged listing, then retried after disappearance and relisting; explicit targets remain strict. Archived threads stop polling but retain their cursor for reactivation.

Unknown live channel scope uses at most 100 volatile candidates, 1 MiB aggregate serialized payload bytes, one concurrent resolver and 256 historical metadata lookup results with LRU eviction. Configured/currently-watched memberships are separate from that cache. Existing transient failures retry at 2–30 second backoff while retaining the original candidate payload; known-scoped frames keep synchronous full-payload SQLite admission. Overflow or an oversized candidate fails intake visibly, preserving committed queue work. Unknown-parent or unwatched-parent raw content is never spooled. **Crash, close or overflow may lose unresolved candidates**; their bodies cannot be reconstructed from IDs if deleted remotely. After positive durable admission, recovery of the full payload and optional parent provenance still requires the current intake scope; parent-based recovery requires following to remain enabled for a configured parent, even when the thread is archived or its history/metadata is unavailable. Excluded queued rows are discarded when drained, not held until following is re-enabled. Close cancels owned metadata fetch/retry work before awaiting drain and prevents late lookup completion from adopting or admitting a candidate.

Without `--gateway`, REST polls continuously every three seconds by default. Each channel poll first reads one latest message. An empty head or an ID at or below the saved cursor needs no full history read; a newer head triggers the existing paginated gap drain. This reduces quiet response bodies without reducing request frequency, at the cost of one extra sequential request and round trip, consuming rate-limit budget for an active channel. The probed message is kept through the drain even if it is deleted between requests. Gateway reconnect backfills use the same path. `--loop 0.1` is six seconds; `--loop 0` is one-shot. Startup validates the authenticated bot, application Message Content Intent, channel access and View Channel/Read Message History permissions before printing `INBOUND_READY discord owner=<id> channel=<id[,id...]|all> bot=<id>` (with `mode=gateway` in Gateway mode). Sending replies additionally needs the relevant send/thread permissions.

For an explicitly supervised continuous REST receiver, `--wake-lanes` enables auto-reopen for an exact registered herdr lane whose tab was closed and whose original OMP session was cleanly retired. Only a pending owner message to that lane can trigger a reopen; a live, explicitly paused, closed, or unverified lane is not reopened. Pending messages for a paused lane remain queued. The lane's final answer to that request is posted back to the original Discord message by the shared receiver, not by a pane-local Discord connection. Use one receiver for a given room, not an overlapping dedicated poller. `--gateway` and one-shot `--loop 0` do not support this feature. Existing monitor arguments, settings, and delivery behavior are unchanged unless the operator adds the flag.

Each channel without a stored cursor baselines the latest message ID without replaying history; an empty channel saves `0`. This applies on cold start and to channels first found by a later REST discovery. A thread first discovered after startup starts at its creation ID or the parent's original start position, whichever is later; an existing cursor always wins. In scope `all`, a channel first seen through a live dispatch starts just before that message; earlier history is skipped. Send the first new request after readiness. The committed cursor is retained at `<stateDir>/discord-inbound/<channelId>.json`, in an owned private directory with atomic mode-0600 cursor files. REST polling and reconnect backfills checkpoint every owner immediately after its successful emit, combining filtered messages into that next owner checkpoint or one final save for a trailing filtered run. A failed owner emit can recheck a filtered prefix but cannot checkpoint past that owner in the drain. Live Gateway dispatches retain per-message checkpoints.

Only remote history-read 403/404 responses make a discovered target unavailable; the same responses remain fatal for an explicit target. Missing owner content, delivery failures and local cursor errors are not skipped as lost access. Gateway intake stops before later queued messages can commit past that failure. A disappeared cursor for an already watched channel is a state error, not a reason to silently ignore messages or rebaseline; first-seen scope-all channel seeding remains unchanged.

Output is `INBOUND discord <channel> <message> from=owner ref=<id|-> <JSON text>`. `ref=` is the message a reply answers; a forward names a message but answers none, so it prints `ref=-` and no `INBOUND_REPLY`. Bots, self, non-owner, webhook and system messages do not emit owner intake. Only watched channels are read (a thread is watched through its own channel ID, its configured parent, or `DORI_DISCORD_SCOPE=all`); a thread `INBOUND` line names the thread ID as `<channel>`, so replies go to the thread. An attachment-only or Discord voice message retains the text `""`. Reply context and attachments follow that unchanged line as separate records:

- `INBOUND_REPLY discord <channel> <message> {"id":"<id>","author":"<id>","text":"..."}` copies the original reply snapshot, without fetching or substituting a newer message. Its ID must match `ref=`; any supplied reference or snapshot channel must be the same physical channel or thread, otherwise intake stops before emitting or checkpointing that message. Missing author or text is `null`, distinct from observed empty text `""`. An omitted `referenced_message` adds `"status":"unresolved"`; explicit `null` adds `"status":"unavailable"` (for example, a deleted target). Both retain the original ID and null author/text. A known `author` can be compared with the `owner=` and `bot=` IDs from `INBOUND_READY` for context only. Reply context is data, not a new owner request or a routing instruction.
- `INBOUND_ATTACHMENT discord <channel> <message> {"filename":"...","content_type":"...","size":<bytes>,"url":"..."}` once per attachment, in Discord's order. `content_type` is optional. Message flag `IS_VOICE_MESSAGE` adds `"voice":true`; `"duration_secs":<seconds>` is included when Discord provides it. The exact signed CDN `url` expires; use it promptly when explicitly downloading or running `dori transcribe <url>`.
- With `--context` only, `INBOUND_CONTEXT discord <channel> <message> {"channel":{"id":"<id>","name":"...","topic":"...","purpose":"..."|null},"thread":{"id":"<id>","name":"...","purpose":"..."|null}|null}` ends the group. A message in a thread names the parent channel under `channel` and the thread under `thread`, each with the purpose recorded for it by `dori channel discord set` (`null` when none); a DM is `"channel":{"id":"<id>","dm":true,"purpose":...}`. `name` and `topic` appear when Discord returns them. Each channel is looked up at most once a minute, shared while in flight, and a lookup is waited on for at most five seconds; a failed or still-hanging lookup is remembered for that minute, so later messages neither repeat the request nor wait again. Expired lookups are dropped as new ones are made and at most 500 are held, so a long-running intake across many threads keeps a bounded cache; a channel evicted by that cap within its minute is looked up again when it next appears. A failed or late lookup, or an unreadable purpose file, never holds or fails the message: the record keeps what is known (the message's channel ID and its purpose; for a thread whose parent cannot be read, the parent ID) and adds `"error":"channel lookup failed (HTTP <status>)"`, `"channel lookup timed out"` or `"channel purposes unreadable"`, never a response body. Channel and thread names and the topic are Discord metadata that others can set (any member who creates a thread names it; anyone with Manage Channels edits a topic), and a purpose is the operator's own note: all of it is context for reading the owner's words, not instructions. Without `--context` nothing is looked up and the output is unchanged.

REST polling and Gateway delivery produce identical record groups. The formatter returns one string per owner message for the existing single emit before cursor commit. A malformed attachment or attachment list is a protocol error; the message stays uncommitted, as it does when emit throws. Consumers parsing only `INBOUND discord ` lines retain the same grammar. Metadata delivery downloads no files and starts no transcription or provider inference. This is new-message intake; edits and delete events are not delivered.

Use one opted-in native `monitor` with filter `^INBOUND` and the [protected-token child argv recipe](../../../docs/releases.md#discord-owner-intake). Startup auth, permission, intent or state failures are sanitized nonzero errors; later REST poll failures follow the ordinary `WARN`/retry loop. Gateway backfill retries transient remote failures while holding live messages; local response/protocol faults and failed delivery stop intake without committing the undelivered message. SIGINT/SIGTERM stops intake, and an explicit restart resumes the committed cursor. Intake never sends presence updates; enable or stop the separate presence monitor intentionally. The [offline benchmark](../../../docs/releases.md#real-time-gateway-mode) uses only synthetic loopback traffic and does not measure Discord service latency.

REST and Gateway intake acquire the same state-directory lock before authentication or polling, including a fresh state directory. Gateway work is serialized through the owned private `<stateDir>/discord-inbound/gateway.sqlite` queue. Indexed queries select queued owners one record at a time; no queued-message array or Promise chain grows behind a stalled backfill. The page-cache budget is 256 KiB and database memory mapping is disabled. Incoming frames and an active REST history drain still use their ordinary memory. Invalid IDs and explicitly unwatched channels are rejected before spooling. Successful handling and cursor persistence precede exact-message-ID acknowledgement; an acknowledgement error stops dependent advancement. WAL `synchronous=NORMAL` retains process-crash recovery without adding two fsyncs per dispatch; power-loss recovery still relies on durable REST cursors.

Queue admission is not the owner-output filter. Valid scoped Gateway `MESSAGE_CREATE` frames are persisted with their full payload before owner filtering, including other users', bots' and webhooks' text, attachment metadata and signed URLs. Scope `all` may admit valid frames from channels not yet discovered by REST. Only owner text is emitted; nonowner rows are discarded during drain, while pending payloads survive shutdown in the private queue. Ownership and `0700`/`0600` modes restrict access; row acknowledgement/deletion is not a secure-erasure promise for SQLite or its journal.

The database is capped at 256 MiB plus journal overhead and reuses freed pages without shrinking its high-water size. Opening an older queue adds nullable admission metadata and lookup indexes in one transaction. Indexes consume the same database budget; building them also requires disk I/O and temporary space. Storage exhaustion stops intake with committed pending work intact. The exclusive SQLite connection rejects a second intake in the same state directory. REST mode refuses to start while Gateway work is pending. Restart with `--gateway` to drain it.

Backfill merges known queued owner payloads with older REST gaps before emitting or checkpointing a newer record. A REST deletion does not cancel a durably queued request. A retained message prefix gets one recovery backfill before replay, including queued scope-all channels with saved cursors. A genuinely new queued channel starts just before its lowest known queued ID, still skipping earlier cold history.

The queue records the durable cursor at admission, not proof of delivery. An older owner frame admitted during an already-started newer emit remains deliverable late, without regressing the cursor. Ordinary stale frames admitted after a completed cursor commit, and direct `accept` calls, retain the existing cursor gate. Cursor equality retains the existing committed-or-baselined ID gate; admission metadata does not prove an emission happened. Same-ID copies coalesce after successful delivery and commit. A crash between emit and cursor persistence can repeat a request; a late emission can also repeat if its exact acknowledgement has not completed.

Legacy rows have no admission position. A pending owner below the cursor is replayed conservatively because older intake may have skipped it; this migration/recovery window can repeat an already delivered request. It cannot restore payloads already deleted by older code. This is not unconditional exactly-once delivery or ordering across arbitrary late arrivals.

Gateway shutdown retains admitted pending work, aborts its own waiting local obligation-ledger admission and cancels owned thread-metadata lookups/retries before awaiting active work. It does not cancel an in-flight history/context HTTP request; an undelivered admitted payload and its cursor remain recoverable on the next Gateway start. Unresolved volatile candidates have the loss boundary described above. Later queued work remains for restart. Genuine storage, protocol, context and delivery failures are not treated as cancellation. Restore storage before restarting after a disk error. Messages not successfully written still rely on REST cursor recovery.

### Discord owner obligation reminders

Dori MAIN tracks owner `INBOUND discord` lines from its CLI or monitor delivery. A complete `dori send discord --reply <owner-message>` confirmed by Discord as a reply to that message supplies the answer receipt. `dori react discord --to <channel> --message <owner-message>` records the exact added reaction (eyes by default). Every accepted reply part must have a valid remote message ID. A plain fallback post, edit, reaction removal or incomplete split send does not supply the corresponding receipt. Direct SDK/API writes bypass this ledger. Check existing remote results before retrying: a remote send or reaction can succeed before a later local receipt write fails.

The synchronous settle hook requests at most three continuations per open obligation younger than 30 minutes; lanes and subagents are exempt. This does not prove answer relevance, a human read or eventual completion. The reminder names each shown message's supported reaction command; do not repeat an already accepted answer or reaction merely because its local receipt is absent.

The private `<stateDir>/owes` directory stores inbound previews (up to 500 characters), send receipts, marks and continuation attempts. Each JSONL snapshot retains at most 200 nonempty rows. Expiry is logical, not deletion; a crash can also leave private temporary snapshot files containing previews outside that row cap. Neither snapshot replacement nor expiry is secure erasure.

Writers reuse per-file owner locks, wait asynchronously and publish capped snapshots atomically. A live holder has no automatic wait timeout; a stale lock whose PID has been reused may look live and require operator repair. Session changes abort waiting monitor admissions rather than waking an old session. Aborting the ledger wait for an already durably queued Gateway message retains its payload and cursor for restart; unresolved candidates have the loss boundary above. Unrelated failures remain errors.

### `dori inbound slack [--loop MIN] [--qualified-routes] [--adopt-legacy-threads WORKSPACE:ACCOUNT]`
Authenticates with `auth.test` and by default prints exactly `INBOUND_READY slack`. Each message is `INBOUND <source> <channel> <thread> <ts> <user> <text>`: `<channel>` is the physical Slack channel ID and the final field is full JSON-encoded text. Existing monitors keep this format.

To migrate a consumer to qualified output, first teach it to accept `INBOUND_READY slack workspace=<team_id> account=<user_id>` and to treat `slack:<team_id>:<user_id>:<channel>` in the channel slot as a Dori destination, not a Slack API channel ID. Then start that receiver with `dori inbound slack --qualified-routes` (and its usual `--loop` setting). All other message fields are unchanged.

Copy the qualified destination into `dori send slack --to` (and retain `--thread` for a reply); a different authenticated workspace or account fails before posting, editing or allocating an upload. Bare physical channel IDs still explicitly select the currently configured account. Qualified destinations also work for library calls with `channel` or `channel_id`. Both receiver formats read from three places, each message once:
- `threads-view`: unread replies in threads the account follows (Slack's own Threads view);
- `own-thread`: new replies in any thread the Dori posted in, tagged or not;
- `unread`: DMs, group DMs and channels with unread mentions.

The Dori's own messages and bot messages are skipped; Slack keeps its existing all-non-self/non-bot policy, not an owner allowlist. Every message the Dori posts records its thread in `<stateDir>/slack-threads.json`, whichever helper sends it, so a guest's untagged reply under a root posted with a raw API call is still found. Version 2 keys each position by authenticated workspace, account, channel and root timestamp, never display name or credential text. Credential rotation for the same identity preserves the position; another account gets separate positions. Reply metadata that disagrees with its enclosing channel or thread stops the poll before any emit or cursor commit. This route identity is not a multi-tenant security boundary.

A nonempty legacy array has no account identity. New posts and inbound polling refuse it without changing it: there is no automatic attribution, reset or resend. Stop old Slack sender/receiver processes first, confirm which workspace/account owns every legacy row, then run `dori inbound slack --loop 0 --adopt-legacy-threads WORKSPACE:ACCOUNT` with that account's credentials. A mismatch is refused. The locked, atomic conversion preserves every position and saves a `SLACK_THREADS_ADOPTED` receipt (scope, time, count); repeating the same decision returns that receipt, and another account cannot reassign it. If ownership is unknown or mixed, preserve the file and resolve ownership before proceeding rather than guessing. Empty legacy arrays need no decision. After conversion, old array-only writers fail closed; do not run an old receiver beside the upgraded one.

Adoption prints only its receipt and exits without polling or advancing positions. Start the normal receiver separately to deliver pending replies; choose `--qualified-routes` only if its consumer has been updated. Output format does not affect account scoping or replace ledger adoption.

### `dori inbound telegram [--loop MIN]`
Startup authenticates the configured bot with `getMe` and requires an empty `getWebhookInfo.url` before printing `INBOUND_READY` or calling `getUpdates`. An invalid identity, unavailable or malformed check, or active webhook is a sanitized nonzero startup error: no cursor acknowledgement is sent, and webhook settings are never changed. Pending checks are awaited; stopping the process while they are pending does not start polling. These online checks run only for an explicit Telegram inbound command, not for offline commands such as `inbound-lag`.

Prints `INBOUND <source> <chat> <thread> <update-id> mid=<message_id> <from> <text>[ file=<kind>:<file_id>][ reply=<message_id>]`, keeping Slack's field order — `source` is `dm`, `topic`, `edit:dm` or `edit:topic`. `mid=<message_id>` is always present (never optional, so later fields never shift; `-` when unknown) and names the Telegram message behind the line: a new message and the edits that replace it share the same `mid=`, so a consumer can pair an edit with the original line. A media message appends ` file=<kind>:<file_id>` (voice, audio, video, video_note, animation, document, photo); the line carries the `file_id`, which a caller can pass to Telegram's `getFile`. A reply appends ` reply=<message_id>`, last, naming the message it answers (`dori decision match` binds by it). In a topic Telegram names the topic's own root as the target of every message that replies to nothing; that is no reply and prints no `reply=`. Only a reply within the same chat names its target; Telegram sends a reply to another chat's message as `external_reply`, which prints none. Live-location shares arrive as a stream of edits carrying only coordinates — those are dropped, not one line each. The corrupt-offset WARN prints to stdout, like every other inbound WARN. Without `--loop` the command is exactly one poll and returns, productive or not. Long-polls `getUpdates`:
- only the configured owner's messages pass (`DORI_TELEGRAM_OWNER_ID`); bot messages never do;
- DMs from the owner always pass; in a group (`DORI_TELEGRAM_GROUP_ID`) only the configured topic (`DORI_TELEGRAM_TOPIC_ID`) does — with a group but no topic, every owner message in the group passes — with no group configured, DMs only;
- delivery is at-least-once: the offset in `<stateDir>/telegram-offset` advances past a message only after its `INBOUND` line is out (dropped updates advance immediately), so a crash replays at worst the unprinted lines — duplicates carry the same update id;
- the full text is printed, JSON-escaped on one line: `getUpdates` cannot fetch a message again;
- edits arrive too: `edited_message` updates are polled and printed as their own `edit` kind, carrying the edited text;
- env ids are validated at start — `DORI_TELEGRAM_OWNER_ID`, `DORI_TELEGRAM_GROUP_ID` and `DORI_TELEGRAM_TOPIC_ID` must match `/^-?\d+$/` after trimming; empty, whitespace-only, `1e3` and `0x10` are refused with an error naming the variable;
- reuses the bot token the skill already stores (`DORI_TELEGRAM_TOKEN`);
- each new owner message gets one 👀 reaction as a read receipt (edits do not), sent in parallel with the `INBOUND` line so it never delays delivery; a failed reaction emits one warning per process, bounded to 300 characters, and the message is still delivered.

### Inbound recovery limits

A live connection, a saved position and recoverable backlog are different. Intake reads only what the configured platform queries still return, plus any payloads already retained on the relevant [Discord delivery path](#discord-delivery-paths). A cursor, offset or queue admission position is not proof that every owner message was delivered.

| Case | Discord | Slack | Telegram |
|---|---|---|---|
| First install (no saved position) | Each channel or thread attached at startup baselines its latest message ID (`0` if empty); it does not replay earlier messages. | The first poll reads the Threads view and unread counts as returned. Each own-thread ledger entry starts at the Dori's first recorded post, not at the beginning of the thread. | Starts at offset `0`. Only updates `getUpdates` still returns that pass the owner and DM/group/topic gates are emitted. |
| Thread or channel created while offline | Configured parent channels follow active child threads at startup, every 10 REST polls and on Gateway `READY`/`RESUMED`. `DORI_DISCORD_THREADS=off` limits explicit scope to configured IDs; scope `all` independently discovers readable text channels and active threads at startup, on Gateway `READY`/`RESUMED` and every 100 REST polls. A followed thread first found at startup baselines its latest ID; if first found on a later refresh, it starts at the later of its creation ID and the parent's start position. Scope-all REST discovery baselines newly found targets. Archived threads are not found by active-thread discovery. | A thread without a ledger entry has no own-thread backfill, but can appear in the unread Threads view (default request limit 20). DM, group-DM and channel-mention notices from unread counts carry no message body. | There is no thread discovery or history fetch. An update from an offline period is eligible only if still returned at the requested offset and allowed by the configured routing gates. |
| Edit behind the saved position | New-message intake only: Gateway admits `MESSAGE_CREATE`, not edits or deletes. | Own-thread polling does not replay an edit whose message `ts` is at or behind the saved position. The Threads view is an unread view, not an edit stream. | An eligible `edited_message` update can arrive as `edit:dm` or `edit:topic` even if the original message predates the offset. Location-only refreshes without text or caption are dropped. |
| Message no longer returned by the platform | A newer REST head triggers history paging (100 per request) back toward the cursor. A successfully admitted Gateway payload may still be delivered if REST omits it; explicit-target history 403/404 errors can block backfill, while discovered targets with those responses are skipped. | The Threads view is partial. Each own-thread poll makes one `conversations.replies` request (`oldest` = saved `ts`, `inclusive=false`, limit 50), with no pagination; it advances to the newest timestamp returned after emission succeeds. | No chat history is fetched. A returned update that is dropped advances the offset immediately; a kept update advances it only after emit returns. The offset cannot recover updates Telegram no longer returns. |
| Rate limit or outage | Continuous REST resumes from saved channel cursors after retryable failures. Gateway backfill retries transient failures with 2–30 s exponential backoff, respecting supported server delays, while admitted work waits. | A failed read or emit leaves own-thread positions unchanged; a subsequent poll can repeat prior output. | A subsequent poll uses the saved offset; an emit failure leaves the failed update uncheckpointed. |

For inbound reads (Discord GET and the read-only Slack/Telegram calls sent as POST), the shared HTTP default allows up to five attempts on 429 or 5xx, with exponential waits from 1 s capped at 60 s and server delay handling. A 429 delay above the retry budget surfaces rather than retrying early; a transport error is not retried within the read call. Mutations may retry a known 429 rejection, but transport errors, HTTP 408 and 5xx leave delivery uncertain rather than triggering an automatic resend.

#### Discord delivery paths

Among Gateway message frames, only payloads actually admitted to the queue are retained, including nonowner payloads until drain. A new scope-all channel seen first through the queue starts just before its lowest known queued ID, not at the start of its history. Unresolved live thread candidates are volatile; discovery, archival or a live connection alone establishes no retained payload. A failed write (including at the 256 MiB database cap) stops intake with committed work intact. Pending admitted work survives an orderly shutdown; REST mode will not start until Gateway work is drained. An emit/checkpoint interruption, an unacknowledged late delivery or legacy-row recovery can repeat a request.

The Gateway queue is separate from the native lane inbox. Discord can route to a bound live lane without `--wake-lanes`; that opt-in enables supervised continuous REST to service pending lane work and reopen eligible retired herdr lanes. It is not Gateway replay or platform history. Slack and Telegram keep positions, not a local payload queue for inbound replay.

### `dori inbound-lag [--limit N]`
Prints `LAG n=<count> p50=<ms>ms p90=<ms>ms p99=<ms>ms max=<ms>ms[ skipped=<n>]` from `<stateDir>/telegram-lag.jsonl`, the meter `dori inbound telegram` writes beside its `INBOUND` lines. The reader works backwards in fixed-size blocks until it has the last `--limit` nonblank records (default 1000), then skips records without a usable lag. Malformed or torn records consume a window slot. Percentiles use the nearest rank, `ceil(p * n)`, over the remaining readings, rather than interpolating.

- one record per handled message: `at` (when the receiver handled it), `tgDateMs` (Telegram's recorded message date), `lagMs` (`max(0, at - tgDateMs)` to clamp host/server clock skew), plus `updateId`, `messageId`, `source`, `chat`, `thread`, `from` and `kind`; an edited message's original `date` is used, so this is not a separate edit-delivery latency measurement;
- a message whose payload carries no `date` records no `lagMs` at all, rather than a `0` that would drag every percentile down;
- the `INBOUND` line itself is untouched — it is a positional contract that consumers parse, so receive lag lives in this separate file;
- a failed append emits one warning per process on stdout (`WARN ...`, bounded to 300 characters); intake and cursor advancement continue;
- new journals are created with mode `0600`, following the state-journal convention. Records include chat and user IDs but no message text or bot token. Existing file permissions are retained, and records accumulate locally until removed by the owner;
- `skipped=<n>` counts records without a finite numeric lag in the window, including missing dates, malformed JSON and the partial last line a kill mid-write leaves behind.

### `dori transcribe <audio-file|url>`
Runs the existing `hooks.transcribe` argv with `{file}` and prints the transcript. Local paths pass through unchanged: no URL size or format policy is applied to them, and local source files are retained.

HTTP(S) downloads stream into a unique private temporary directory and owner-only file. `transcribeMaxBytes` defaults to **26214400 bytes (25 MiB)** and accepts a positive safe integer in the Dori config. The limit counts actual streamed, decompressed bytes across all chunks, not a missing, zero or claimed `Content-Length`; exceeding it aborts the download before the hook. A declared over-limit size is rejected before reading the body.

Before calling the hook, Dori identifies downloaded WAV, Layer III MP3, Ogg, M4A/MP4 or FLAC and checks any declared MIME type against that identification. Missing or generic octet-stream MIME is accepted only for a recognized format. These are bounded metadata checks, not full codec decoding.

- Ogg: a complete Opus or Vorbis identification packet must be present in the first 32 beginning-of-stream pages. `video/ogg` is accepted when supported audio is present; `audio/opus` requires Opus. Mapped Opus channels require the declared stream counts and channel mapping.
- M4A/MP4: a supported major brand and a `soun` track handler are required. `video/mp4` is accepted when the container has an audio track. The box walk checks at most 4096 boxes and can find `moov` after `mdat`; fragmented files are supported.
- MP3: ID3 alone is not audio. Indexed Layer III uses the frame header; free-format Layer III needs three complete frames with compatible headers and matching, padding-adjusted spacing, with the next header within 8192 bytes.

Use a local path for unsupported Ogg codecs, very short free-format clips, or other files outside these inspection bounds.

**Compatibility change:** raw PCM, unknown/truncated signatures and MIME/signature contradictions in URLs now fail before transcription. Convert unsupported input to one of the listed containers, fix an incorrect server MIME, or supply a local file path for a custom hook format. Size errors name `transcribeMaxBytes` and how to adjust it; other download refusals give their reason, the setting and a corrective action on one line. The downloaded file and directory are removed on success, overflow, failed downloads, rejected formats, and failed or empty transcription. Errors exit nonzero.

### `dori heavy <label> -- <command ...>`
Waits until load is under `heavyMaxLoad` and one of `heavySlots` is free, then runs the command and frees the slot when it exits. A slot held by a process that no longer exists (or a zombie) is taken over. Use it for full builds and test suites. Installs, focused tests and git do not need it.

## Staged Dori updates

`dori upstream` is the maintainer source-porting interface, with its own required `--config FILE`, dispatched before normal Dori config/state loading. It is separate from consumer `dori update`. Without `promotion`, it only stages source candidates and never commits, pushes or replaces live Dori. An explicit owner-approved promotion policy enables exact-source publication and optional managed herdr replacement after all checks and fresh review pass. That policy is standing authorization for its configured target, not permission for arbitrary repositories or sessions. Installation and boot never enable it. Neither mode upgrades global Bun, changes global model policy or updates ULW.

The complete example is [`examples/update.config.json`](../../../examples/update.config.json), relative to the repository root. Its paths resolve relative to that file: it reads this checkout as `localSource` and writes an independent sibling staging directory. Worker/reviewer commands are explicit operator argv, separate from the installed lane defaults; use the source-only native launcher, not a side role wrapper or stock OMP. For the example's bare `omp`, prepend the prepared native cache for that invocation as below, or configure its printed absolute `bin/omp` path. Model/thinking selectors remain explicit examples, not controller defaults.

The native agent route targets the observed OMP 18.18.8 CLI/protocol. Both agents use `--no-pty`; the reviewer additionally uses `--no-lsp` to disable LSP tools, formatting and diagnostics, while the worker retains normal navigation support. User-supplied `--dori-role`/extension/profile flags are rejected. The controller loads its own trusted guard with an explicit `-e` for each agent (reviewer: exact read-only set; worker: built-in search/edit/shell tools only); normal role sessions and their pinned extension behavior remain unchanged.

Agent commands may declare `engine:"omp"` or `engine:"external"`. Use `"omp"` for a custom actual compiled CLI executable with a readable, PID-preserving command prefix to apply native final-message parsing and capability guards. Without it, shared OMP classification reads the argv template, including Bun's `run` form, after leading `NAME=value` assignments and readable nested `env`/launcher prefixes. Direct OMP and known exec-preserving `env`, `nohup`, `nice` and `stdbuf` forms are usable; native checks read the OMP argv after that prefix and the controller preserves the complete configured argv. Attach interpreter option values with `=` as in `bun run --preload=FILE omp`; `bun run --smol omp` is also readable. General harness/lane classification still recognizes package runners and potentially forking launchers, but automated native updates refuse `timeout`, `caffeinate`, every `setsid` form (including conditional forks), `npx`, `bunx`, `bun x`, `npm exec`/`x` and conservatively unreadable runner variants at config load and again before model execution. The error requires a `PID-preserving` launch, even with explicit `engine:"omp"`: the launched PID must equal the guard receipt's PID; ancestry is not authorization. `npm exec`/`x` is unparsed unless `--` immediately precedes its command, because npm would otherwise consume OMP/controller options. Possible-OMP lanes still require trusted session state for goals and pause. An unreadable `env` prefix (`-S`, an unknown option), Bun/Node interpreter prefix, OMP-naming shell string or external wrapper behind a launcher also remains refused even with `"omp"`. Only `"external"` opts out: that trusted wrapper must run a real fresh model context, enforce read-only review itself and return only the final structured verdict line. A native OMP argv must end with `{prompt}`; controller options precede that positional (and a `--` immediately before it), and resume/continue/restore/fork flags remain forbidden. Whatever approval policy the CLI needs for edit/write/bash in print mode must be configured by the operator; the controller never adds auto-approval. Historical `env -u --profile` startup claims did not prove successful native scope validation: argument-printing probes stopped before receipt comparison. The current `env -u` and `stdbuf` regression sources exercise full worker/reviewer receipt validation without a provider; they do not claim a real model run.

Before either native worker or reviewer starts, the job-owned `--config` overlay sets `disabledProviders` to `native`, `mcp-json`, `omp-plugins`, `agent-plugins`, `claude`, `claude-plugins`, `codex`, `gemini`, `opencode`, `cursor`, `windsurf`, and `vscode`, and preserves `mcp.enableProjectConfig:false`. OMP 18.18.8 loads this overlay before binding discovery settings and loading MCP, disabling every MCP-capable discovery source before server startup and instruction injection. This uses the supported [`disabledProviders` setting](https://github.com/can1357/oh-my-pi/blob/v18.18.8/packages/coding-agent/src/config/model-settings.ts#L77-L82) and [capability filtering](https://github.com/can1357/oh-my-pi/blob/v18.18.8/packages/coding-agent/src/capability/index.ts#L360-L400); it does not merely hide MCP tool names. The tagged setting declares no environment override; the rebuilt environment also excludes `PI_CONFIG_FILES` and reserved `PI_*`/`OMP_*` capabilities. No live/global client settings are edited.

The native reviewer guard awaits `api.setActiveTools(["read","grep","glob"])` and verifies the exact active set before agent start and provider requests. CLI `--tools` alone is insufficient on the target runtime. A persistent `tool_call` hook also blocks every other tool **before approval/execution**. Blocked attempts remain in its nonce/job/source/PID-bound receipt and invalidate readiness, even if a later active-set readback is clean. The controller requires the actual scope receipt plus successful terminal model output. Its final reviewer text must be exactly one compact marker/JSON line, with no surrounding prose or code fence. Actual inherited MCP startup or instructions remain an isolation finding even with a clean tool roster.

The native **worker** guard (`src/update/worker-guard.ts`) is the same mechanism with a different allow-list: it awaits `api.setActiveTools` to the built-in `read, grep, glob, find, ast_grep, ast_edit, edit, write, bash, lsp, todo, wait, eval` that exist, reads the set back (extras fail the run; `read`, `edit`, `write` and `bash` are required) and gates every call. MCP, web, GitHub, subagent (`task`), memory and skill-management tools are denied, so untrusted upstream content cannot steer the owner's global MCP servers. A denied attempt is recorded in the worker's nonce/job/PID-bound receipt (`blocked`) for the reviewer, but does not by itself fail the port. The worker keeps its normal shell and edit power as the operator's OS user: path confinement is by instruction and review, not by the guard.

`check` observes exactly `remote` plus the full `ref`. A head equal to `baseUpstream` is unchanged. `stage` explicitly exercises the current exact head even when it is the baseline; its request receipt says `manual-current-head`, never a detected new commit. Both commands deduplicate an already attempted SHA, including failures and rejections. An unchanged head never spends another model run. `watch` is the same cycle with a configured interval and one controller lock for its lifetime. It stops on active or ambiguous work. Installation and normal boot start no updater.

Every command has a unique `name` (letters, digits, `.`, `_`, `-`), nonempty `argv`, positive `timeoutMs`, and for provisioning/checks an optional candidate-relative `cwd`. `engine` is valid only on worker/reviewer; `modelAgentDir` accepts `~`. No shell string is constructed. All source preparation uses independent ordinary clones, no linked worktree or live-tree Git operation.

Every agent command must consume `{prompt}` or `{brief}`. `{candidate}`, `{job}`, `{agentConfig}` and `{sessions}` are also available per argv element. Worker and reviewer run in separate new processes with separate config/state/session/HOME/cache/tmp directories and contexts. Native OMP commands are rejected if they carry resume, continue, restore or fork flags; an `engine:"external"` wrapper is not inspected for them and owns its own fresh-context contract. No automatic approval or credit/reset redemption is implemented.

Direct OMP commands are pinned to `--mode json`: the controller reads completed assistant `message_end` text only and requires a matching terminal `agent_end` plus successful process exit. User/tool content, streaming deltas, `turn_end` repeats and nonterminal ends cannot supply a verdict. The final message attests observed provider/model separately from the requested selector; a different observed exact provider/model holds the candidate. A wrapper's final plain-text marker is accepted only as the wrapper's trusted output contract.

`modelEnv` lists the exact host environment **names** a model client may inherit, such as `ANTHROPIC_API_KEY`. Their values are never in configuration, argv or receipts and are redacted from private child logs. Checks inherit none of these capabilities. By default the OMP agent directory is fresh too. An explicitly configured `modelAgentDir` is a trusted authentication/provider-settings reference outside source/staging, used only by model clients and never copied or snapshotted; it is never a session/state directory. Disabling discovery providers preserves this reference for model/auth resolution. Extra configured model/provider names alone do not establish session/state merging. `--no-session` and task-owned session paths keep normal session history separate; inherited MCP startup/instructions, writes to trusted/live client settings and credential copies remain disallowed. The native config overlay and Dori's generated `DORI_CONFIG` JSON are separate files.

Every launch rebuilds its environment: dedicated `HOME`, Dori config/state, harness home, XDG paths and tmp; a job-owned shared cache for frozen installs; and, for model agents, a native session directory and isolated `DORI_HERDR_SESSION`/`HC_SESSION`. Parent pane/workspace/session IDs and unrelated environment variables are absent. `DORI_RUNTIME=herdr`, `DORI_TELEMETRY=0` and `DO_NOT_TRACK=1` apply only to automated launches. Model authentication is an explicit trusted capability. This is environment/path isolation, **not an OS sandbox**: configured commands and model tools still run as the operator's OS user.

Runtime paths use a short per-command `/tmp/du-<identity>` symlink into the job's durable `runtime/ORDINAL` directory, so `HOME`, tmp, all XDG paths and native session/config paths remain short enough for Herdr/HC Unix sockets even under a deep staging root. Shared caches are reached through an owned link inside that directory; their actual data stays in the job. Each runtime's private `runtime-paths.json` binds its alias, real directory, cache, configuration hash and OS uid. Existing foreign paths, mismatched links or ownership receipts hold the launch without replacing them. The detector has the same mapping under `root/detector`.

`GIT_CEILING_DIRECTORIES` is the canonical real runtime directory: Git discovery from runtime tmp paths stops there, including through the short alias. Repositories deliberately initialized below that boundary remain discoverable.

These aliases and real runtime data are intentionally retained after exit or interruption: the controller cannot assume every descendant has stopped. `/tmp` aliases are not recovery snapshots or live activation links. After confirming **all** owned descendants have stopped, an operator may unlink only an alias whose uid and exact symlink target still match its retained ownership receipt; do not recursively remove its target or unrelated `/tmp` entries. Missing aliases can be recreated only from a matching ownership receipt; collisions require inspection. Recovery restores code/application data, not old runtime processes or their aliases.

Before model work the job freezes base-upstream, current local source (including dirty/untracked adaptations) and exact new upstream, with SHA-256 manifests and a union of changed paths. Local native/ULW lock+patch payloads, `native-addon/` frozen manifests and admitted `ref/omp-ulw/` code are opaque frozen dependencies, not model update targets. They are carried byte for byte into the incoming candidate, retaining ordinary changed-path, source/check/review and recovery coverage. Manifests still bind `ulwPresent` and `ref/omp-ulw/` presence/absence; a worker/check must not install an absent library, and a conflicting incoming library holds rather than being replaced or deleted.
Source manifests record excluded nodes, and admission checks those exclusions before copying or executing source. A pinned base or incoming upstream may exclude **only real `.git` directories**. Any other excluded path holds preparation before the worker, including tracked `bin/dori`, upstream `node_modules`, `.omp`, runtime directories, other `ref` checkouts and private-key/environment filenames. Git ignore rules do not select source: ordinary dirty, untracked and ignored adaptations remain hashed, frozen and required in changed-path coverage.

The local input additionally permits real `node_modules` directories and a narrow non-source metadata boundary: root `config.json`; `.DS_Store`, `.env`, secret `.env.*`, `auth.json`, `credentials.json` and `.pem`/`.key`/`.p12`/`.pfx` files; and `auth`/`credentials` directories within the opaque `ref/omp-ulw` library. `.env.example` and `.env.sample` remain source. These credential/runtime inputs are never copied to the candidate or recovery source. Every other excluded local node holds preparation, including local `bin`, state/session/cache/tmp/evidence directories, other `ref` checkouts and opaque-library `bin`, `.cache`, `.omp` or global extension code. Keep runtime/application data outside the admitted source distribution; explicit application-data recovery is a separate input. The controller never silently drops those excluded code containers to finish a port.

Workers must not install dependencies or create `node_modules` directories at any depth; on entry to verification, before configured provisioning begins, candidate admission permits only real `.git` metadata. The controller alone owns dependency provisioning.

Candidate binding permits **only real `.git` and `node_modules` directories**, at the root or nested paths such as `ref/omp-ulw/.git` and `skills/dori-mode/scripts/node_modules`. These are exact path components, not prefix matches. Every other exclusion holds before/after trusted provision commands, at final source binding and after each check/review, even when the admitted-file hash is unchanged. Frozen-input checks and source snapshot/restore use the same admission boundary, so an excluded payload cannot disappear behind a successful hash comparison or recovery copy. Normal provision changes to admitted Dori source still precede the single final freeze; installed dependencies remain governed by trusted explicit provisioning.

Admitted source symlinks/special files fail rather than being followed; permitted Git/dependency metadata must itself be a real directory. This is a source admission boundary, not an embedded-secret scanner: keep source free of credentials. Neither the controller nor its worker investigates, ports, fetches or updates ULW.

The worker reconciles every changed path and emits a bound coverage receipt. It starts from incoming upstream rather than receiving a blanket old-source overlay. The controller then runs **every configured provisioning command** as trusted explicit preparation: frozen-lockfile installs for root, skill and extension, followed by the configured `bun run format` normalization in the example. Preparation may rewrite admitted Dori source, but frozen inputs, the opaque local ULW pin and Git metadata are enforced before and after every provision command, including failure. There is no automatic formatter, repair loop or retry.

The worker performs a three-way integration: it carries local edits and removals forward while integrating the delta from base to incoming upstream. Starting from an incoming checkout does not authorize restoring locally removed code or tests. In particular, removed wording, source-text, forwarding and incidental-default assertions are not missing behavior coverage to resurrect; consumer-visible behavior and boundary regressions remain required.

Only after all provisioning succeeds does the controller freeze and persist the final `sourceHash` and `ported-source.json`, then run **every configured check**. Provisioning receipts record actual preparation exits, not passed verification of that final hash. Check and review receipts must bind the final post-preparation source; any admitted-source mutation during a check or review holds the candidate rather than rebinding old evidence. All commands retain stdout/stderr/exit/time/process receipts. A fresh reviewer independently covers `upstreamCoverage`, `localAdaptations`, `correctness`, `isolation`, `verification`, `security`, `failureRecovery` and `scope`; its structured `DORI_UPDATE_REVIEW` response must bind the exact checked source, provide evidence for all eight items, findings and explicit limitations. Plain `VERDICT: CLEAR`, missing/malformed output, unavailable review, unknown items and stale source never grant readiness. Requested and observed model identities are separate receipt fields; unavailable observation stays `null`.

The **entire final assistant response** must be one physical line: `DORI_UPDATE_REVIEW ` followed by one compact JSON object, with no introduction, explanation, bullets, markdown fence or surrounding text. An approval requires all eight items to pass and `findings: []`. Any unresolved finding requires rejection; nonblocking observations belong in the relevant checklist evidence or limitations. The controller does not strip surrounding prose or reinterpret an invalid approval as readiness.

Private artifacts live in `root/jobs/JOB_ID/`: ordinary `candidate/`, frozen `inputs/`, `prepared-source.json`, `ported-source.json`, coverage/review briefs and receipts, per-command logs, generated `runtime/`, `job.json` and `report.json`. The report contains exact upstream/base/local/candidate hashes, actual check exits, independent verdict/limits, candidate path and rollback inputs. `ready` still means **candidate only**; automatic publication/deployment has a separate durable promotion record and never rewrites that readiness evidence. Candidate phases remain `prepared`, `porting`, `verifying`, `reviewing`, `ready`, `failed`, `rejected` and `interrupted`. The accepted upstream baseline advances in persisted state only after the configured complete promotion succeeds. Configuration identity stays bound to the root; changing policy requires a new staging root, not editing its historical baseline.

Stdout emits path-free JSON `DORI_UPDATE` events; detailed status and receipts remain private. For stage-only watching, the owning session's monitor tool can run `watch` and filter phase/candidate/held/error events so unchanged observations stay quiet. Automatic live replacement instead needs the external supervisor below: an in-session watcher dies with the session it replaces. Neither form posts periodic owner progress merely because a detection interval elapsed. `status` prints private local reports and must not be forwarded wholesale to a messenger.

Optional `reporter` is a trusted argv command consuming `{text}` (also allowed: `{job}`, `{upstream}`, `{phase}`). Its text is a fixed path-free JSON projection with hashes, check exits, verdict and limitation count; detailed findings remain in the local artifact. It can call existing `dori send slack|telegram|discord --to ... --text {text}` using the operator's actual target and trusted executable path. Set `reporterEnv` to exact messenger token/cookie names; only the reporter inherits them. No target/channel is built into product code. Sending intent is durable before the external write. A reporter that never started or exited nonzero is `failed`; one killed or lost after it started is `ambiguous` and `sending` after a crash becomes `ambiguous` on recovery. Neither is ever resent, neither changes the verdict, and neither blocks later updates; both appear in `status` and make `check`/`stage` exit 3.

### Recovery drill

Stop the watcher in its owning session first. Inspect retained process receipts and establish that all old children have stopped; the updater never guesses from an aged lock, kills an unknown PID or resumes an interrupted model/check. For an active job, `dori upstream recover --config FILE --ack-stopped ID` is the explicit acknowledgement. It clears active ownership and keeps the SHA deduplicated. A job that was still mid-run becomes `interrupted`; a job that already had a complete verdict (`ready`, `failed`, `rejected`) keeps it, and a `ready` verdict whose source no longer matches becomes `failed`. A live controller or foreign-host lock holds recovery.

Acknowledgement never retries or rebinds a terminal failed candidate. To evaluate a corrected controller against the same upstream SHA, use a separate configuration and a fresh isolated `root`, retaining the previous root and its receipts unchanged. This is a new run: it must perform a fresh port, every configured check and a fresh independent review; no archived check or verdict grants readiness. Never rewrite the old state's `configHash`, job phase or receipts.

If the watcher died while idle and there is no active job, `dori upstream recover --config FILE --ack-stopped none` acknowledges the stopped controller alone and retains its lock evidence in `recovery-ack.json`. Corrupt lock/state records require manual inspection; they are never guessed away.

The following commands discover the existing terminal job and create **fresh sibling directories**. Run them from the checkout with `jq` available; `config` is the existing example. First run the isolated candidate with its dedicated application data under `root/application`, then stop that candidate's state writers. `--app-state` must name that existing task-owned data, never the owner's live state or model-client directory. If skill `DORI_STATE_DIR` and harness `DORI_HOME` are separate, supply their common owned data container so both relative trees are preserved.

```sh
config="$PWD/examples/update.config.json"
root="$(dirname "$PWD")/dori-update-staging"
app_state="$root/application"
job="$(jq -r '.jobs | to_entries | last | .value' "$root/state.json")"
stamp="$(date +%s)"
snapshot="$(dirname "$PWD")/dori-source-state-$stamp"
restored="$(dirname "$PWD")/dori-restored-$stamp"
bun skills/dori-mode/scripts/src/cli.ts upstream snapshot --config "$config" --job "$job" --output "$snapshot" --app-state "$app_state"
bun skills/dori-mode/scripts/src/cli.ts upstream restore --config "$config" --input "$snapshot" --output "$restored"
jq '{phase, sourceHash, applicationStateHash, applicationState, candidateOnly}' "$restored/recovery.json"
```

`snapshot` requires no active/ambiguous updater work and freezes source, frozen inputs, updater control state and command receipts/logs. With explicit `--app-state`, it separately freezes actual application lane/paused state, receipts, monitor specifications, session identity metadata and inbound cursors. This state never enters source snapshots or model prompts. Application authentication, environment files, configuration/settings, private keys and personal client directories are excluded. No application state is inferred: omitting the flag records `applicationState:null` and produces a code/control-evidence snapshot only.

`restore` validates source, application-data and control/evidence manifests before writing a new destination: mutable `candidate/`, mutable `app-state/` when supplied, frozen `inputs/`, archived original control evidence and an explicit `interrupted` recovery record. It preserves application data bytes and statuses; it does not rewrite paused lanes, launch monitors or reconnect old processes. Point a new owned Dori config's `stateDir` and `DORI_HOME` at the restored relative trees before an explicit isolated restart. `applicationManifest()` exposes the admitted application-data hash for comparison, and the existing Registry/Store/cursor/monitor readers can read the restored data normally.

Restored historical checks/review grant no source readiness and are never loaded into the running watcher. Admitted opaque `ref/omp-ulw/` source and its presence/absence are restored with the code; installed packages, Git objects, model sessions/history and authentication are not. No existing source, live state or failed candidate is deleted or overwritten. State writers must remain stopped during a snapshot; changed inputs, links and special files fail rather than producing a misleading recovery copy. This is a source/application-data recovery procedure, not an OS image or an embedded-secret scanner.

Exit codes: `0` unchanged/ready or completed status/recovery, `3` failed/rejected/held candidate or failed reporter, `4` detector unavailable with proven stopped ownership (retryable), `5` updater root locked by a verified live same-host controller (retryable), `2` configuration/operation error, `130` requested interruption. A timed-out detector is retryable only after its owned process group has stopped and both output pipes have drained; surviving or unproven descendants remain held. Before watcher activation, run `bun test ./test/update*.test.ts`, the repository checks, and a real explicitly configured `stage` cycle, then exercise the generated native guard and application-state restore on owned fixtures.

### Owner-authorized automatic publication and deployment

The optional `promotion.publish` object defines `remote`, full branch `ref`, `author: {name,email}` and, for GitHub, `github: {gh,credentialHome,requiredChecks}`. The remote must be credential-free. `gh` is the actual trusted executable, `credentialHome` references existing controller-only GitHub authentication in place, and `requiredChecks` lists the exact required check names. Local Git remotes support isolated real-Git proofs without a GitHub capability. Workers, reviewers and checks do not inherit publication credentials.

Publication derives its public manifest from the checked `ported-source.json`, verifies every exported byte and executable mode, and excludes the opaque `ref/omp-ulw` checkout. It never publishes the candidate's Git metadata, runtime state, model sessions or ignored private files. A separate own-repository commit preserves the exact expected main parent. The controller pushes an owned branch, opens or resumes its GitHub PR, requires successful checks for that exact commit, and only then fast-forwards the configured target. It never forces a ref. Concurrent target changes hold the job. Durable intent plus actual remote readback prevents a crash after push from repeating publication or model work.

When `reporter` is configured, promotion awaits a separate durable notice before pushing main and another before the first forward runtime stop. These are notifications, not approval requests. Accepted notices are reused only for the same job, action, exact publication/deployment intent, configuration and command receipt. A failed, unresolved or incomplete attempt holds the effect without automatically resending; terminal reports preserve the separate notice receipts. Without a configured reporter, existing non-notifying library operations remain unchanged.

Before new publication intent, the public frozen local tree must equal the observed target tree, so an owner commit cannot disappear beneath a newer manifest. Optional `publish.initialSource: {main,sourceHash,exportHash,baseUpstream,upstream}` authorizes one explicitly reviewed initial uncommitted source cutover. The exact main, reverified frozen local manifest, approved final public export and authentic upstream pair must all match. A durable job claim prevents reuse by another job; the publication record preserves its basis and pins for resume. It is not a concurrency or review override. Configure these pins before the state root's first use and never edit/remove them: configHash is write-once. After deployment changes local source, normal tree matching resumes without a config rewrite. Initial historical replay is labeled separately from a newly arrived upstream update. A confirmed published commit remains published when it is an ancestor of later main; deploying that older source holds rather than undoing owner work.

Initial-source publication tests share only a checked immutable export-hash reference; every scenario still prepares its own isolated candidate and receipts. Pass the existing shared reference to bootstrap fixtures instead of repeating reference-only Git preparation inside each case's execution deadline.

Terminal held promotions retain their evidence and baseline but do not block detection of newer upstream SHAs. Pre-record tree, pin and one-time-claim mismatches are durable terminal holds, not silent publishing retries. The same attempted SHA remains deduplicated and is not silently re-ported. Retryable busy/pre-stop preparation/lock holds do not consume the terminal failure notification. GitHub's stale `blocked` mergeability after successful exact-head checks remains waiting, not approval. CI waiting retains its first deadline: the configured check timeout sum, bounded to 1–24 hours. Missing evidence or unresolved mergeability at that deadline becomes a terminal hold with one notification.

An owner commit on main, publish-only operation or rollback after successful publication can leave localSource behind main. The normal guard then holds until an operator reconciles source. Prepare an owned checkout of the actual target commit, retain the admitted opaque local ULW pin unchanged, inspect the owner delta and verify that source, then retarget the already-configured stable localSource link. Never rewrite configHash, baseline, old job evidence or publication receipts to bypass the guard. Admission runs at publication time after ready, so an unreconciled source can spend one doomed port per newer upstream SHA; same-SHA dedup still applies.

`promotion.deployment` is optional and requires Linux or macOS process identity support. Configure `releaseRoot`, stable `liveSource`, operator `home`, `doriHome`, `doriConfig`, `stateDir`, private `bun`, session-runtime binary, `pane`, `sessionId`, `model`, shared `restartLock`, fixed `launcherPath` and bounded `healthTimeoutMs`. Omit `omp` for a new release's bound source default; supplying it is an explicit external-native override. Older no-lock records keep their original explicit-native contract. `runtime` is `herdr` by default (`herdr`, `w1:p2`, optional `herdrSession`) or `hc` (`hc`, `t7`, optional `hcSession`). On macOS the final identity check and signal remain separate calls: a reused PID cannot be excluded as with Linux pidfd binding. Optional `stopTimeoutMs`, `monitorBootstrapFile`, `quiesceCheckpointFile` and release-relative `shims` still cover the operator's runtime. Initial real-directory conversion can retain `legacyOmp` only when it matches the captured running executable; later rollback uses the prior recorded toolchain. The pane/session/state directory must describe that owning Dori.

Optional `nativeStopMode` accepts `"ui"` or `"signal"`. Omit the property to retain the existing signal stop and canonical config/hash; there is no new default. `"ui"` applies only to the forward `stopRuntime` handoff on Linux/herdr. Other platform/runtime combinations hold before recording stop intent; they retain their default signal deployment support. Failed-start and rollback cleanup of the new runtime retain their existing identity-bound signal behavior. Normal UI exit was exercised with Native 18.20 on Linux/herdr; other native versions and renderers require separate validation, and the historical SIGTERM failure cause remains unconfirmed.

A failed or missing UI-key acknowledgement does not prove that the key was undelivered. The controller still waits for the bound native exit and bare root shell. If either remains unsettled, restart keeps its pending intent and deployment remains retryable at the forward stop step; neither declares that the possibly exiting old actor was successfully rolled back. A later invocation resumes observation without sending another key. Rollback after the observed forward stop and cleanup of a newly launched runtime remain unchanged.

UI handoff requires an external controller and an ended current Dori turn: let the target become actually idle before the controller stops it. A controller launched as the target's descendant is held. A quiesce checkpoint never permits a UI key while native metadata still reports working, and no Ctrl+C is sent. Before one Ctrl+D, the controller reobserves the exact pane, root, foreground, native process, source and session together with recognized empty native input. A draft, unknown footer or pending approval holds without a key or signal fallback. The journal persists `nativeUiExitRequestedAt` before dispatch; recovery never resends even after an uncertain key result. Native exit, PID-reuse checks and a positively observed bare root shell remain the completion authority.

The deployment transaction verifies and prepares the committed managed release before touching the live source. A legacy real source directory is preserved by rename, not deleted. It journals the old pointers and exact PID/start/boot/session identities before stopping anything, switches only configured links, and resumes the same native session by reference. Existing application state, paused goals, cursors, credentials, model history and global model policy stay in place; they are not copied into a release. New health requires the correct role/session/PID/code, desired monitor descendants and fresh intake heartbeat. Process existence or a printed success string is insufficient.

Managed startup, rollback and restart bind the actual native entrypoint, Bun bytes and owned per-process `{"update":{"auto":false}}` overlay. New default receipts additionally bind the complete native source identity, exact launcher and actual official addon bytes, plus the selected ULW base/patch/result identity; a launcher hash or 18.20.0 version alone is insufficient. Preparation occurs before admission, and reuse checks source drift. A configured external `omp` is marked `nativeOverride`, not patched-source evidence. Managed default role sessions explicitly load their prepared Dori extension once and route its default ULW import to the prepared dependency; explicit external ULW paths remain user choices. Global native/Bun installations and model/auth settings are not rewritten. Explicit process-local `OMP_ULW_SCOPE_FILE` is forwarded as a path, never copied as policy contents.

`launcherPath` is the operator's stable restart executable slot, for example `~/.dori/bin/managed-native-restart`. The transaction preserves that slot and switches it to an owned script pinned to the prepared controller release. Do not point this field at a controller `.ts` source file or at the outer delay/model-watch wrapper. Before first conversion, a protected initial delegate may invoke `bun FIXED_CONTROLLER/src/update/deployment-launcher.ts DEPLOYMENT_CONFIG_JSON`; the outer helper delegates to the stable slot before any signal.

Ordinary replacement/restart holds busy or approval-blocked actors. An initial self-handoff may use a private, expiring, exact-intent/commit/source/PID-bound quiesce checkpoint; it is not a reusable busy override, and approvals still block it. A trusted first-boot monitor bootstrap supplies `{version:1,sessionId,monitors:[{name,argv,filter,cwd}],intake:{path,monitor,maxAgeMs}}` and optional recorded running monitor PIDs. The controller revalidates ownership before cleanup. New persisted starts remain compatible with legacy rollback. Token-loading monitors must load their own credentials inside protected child launchers, not inherit a token or sudo password from the resumed Dori.

Script-based monitors can share the native actor's foreground group. Only managed deployment may disregard their exact attested processes: the native actor must be present in its actual foreground group, and each ignored monitor must match its desired command/cwd and saved incarnation as that actor's descendant. Initial bootstrap needs a `runtime` receipt with `pid,startTicks,bootId,executable,imageDev,imageIno,pane,role,sessionId,startedAt`, plus each `running` entry's complete `identity` (`pid,startTicks,bootId,executable,imageDev,imageIno`). Thin `{name,pid}` entries alone do not grant this exception. Managed actors use their current owned runtime-health record and persisted monitor specs, including monitor start ticks. Unknown shells, a foreground root shell, stale/reused/foreign identities and missing proof still hold. Generic harness delivery and its foreground-shell rules are unchanged.

Launch identification and failed-start cleanup use the same strong foreground attestation for managed actors, including a prior managed rollback. A matching live but unattested process is a hold, not evidence that no process launched. Starting or resuming a launch requires a positively identified bare pane-root shell with no live pane owner or children, including background or suspended descendants; a native actor's Bash monitors never satisfy that condition. Unknown metadata and unsupported shell flags hold rather than typing a second launch into an existing process. The pre-role, no-shell startup cleanup path remains bound to its exact journaled executable, argv and chronology, and initialized actors must be idle without approval before cleanup.

A shell alias is admitted only when its absolute kernel argv0 resolves to the observed executable and the reported shell name remains bound to that argv0, for example `/bin/sh` resolving to `/usr/bin/dash`. A matching display name without exact canonical image and incarnation proof is insufficient.

An initial legacy rollback may have no runtime-health writer. Only the controller's journaled rollback launch and health observation may then bind the new native incarnation to the preserved monitor commands, actual working directories and current descendant identities. This separate rollback proof does not rewrite the original bootstrap or authorize another launch. Unknown shells and changed incarnations still hold. Native `ps` observations use the observer's resolved time zone, so a caller's different `TZ` does not alter process-start chronology or relax its time window.

Failed-start rollback discovery and its pre-signal safety attestation retry fresh observations within bounded windows, so an exiting monitor child cannot turn one transient snapshot into an immediate terminal rollback failure. Each attempt still enforces the exact process, image, argv, chronology, session, idle and approval guards; deadline or cancellation never authorizes signalling an unverified process. Observing a completed bootstrap rollback is read-only and requires the genuine `rolled-back`/`done` journal, `rollbackHealthyAt`, matching rollback process/runtime and original source proof, and the unchanged bootstrap with current monitor incarnations. This completed observation grants no launch capability and never rewrites the journal step or original bootstrap.

Re-entering a completed rollback only waits for fresh bounded health to match its saved runtime receipt. It does not change `done`, persist the record again, restore pointers, signal or launch another process. Live replacement and kernel-bound cleanup require Linux `/proc` and pidfds; other platforms hold before native effects, while portable detection, publication, pointer and admission checks remain enabled. Pointer backups preserve the symlink inode itself rather than following its target on Linux and macOS, including dangling links.

Herdr `done` is admitted as idle-equivalent only when process-bound native metadata does not attest `working`. Native working metadata remains authoritative and requires ordinary idle convergence or the exact one-shot quiesce checkpoint. Approval and identity guards still apply. Pre-stop command/lock failures get one persisted 1-hour failure-retry window; expiry is a terminal hold without signalling the actor. Verified busy waits do not consume that failure window. Malformed source, integrity failures and post-stop ambiguity do not acquire retry permission.

The intake heartbeat is a decimal epoch-millisecond timestamp written by the configured intake monitor. It must be an owned regular file without group/world write permission; use mode `0600`, including for an existing receipt. A live process and a fresh but group-writable pulse do not satisfy deployment health.

On failed startup or health, rollback restores the prior execution source and session when that can be done without interrupting new owner work or approvals. An ambiguous identity or newly busy actor holds for inspection instead. Runtime rollback does not rewrite published GitHub history: main and the running release can temporarily differ, and the promotion record distinguishes them. `dori upstream restart --config FILE` uses the configured managed restart lock and the same identity/health checks; existing model-watch helpers must delegate before sending any signal.

### Resident supervision

Run `scripts/update-supervisor.ts --config FILE --controller DIRECTORY --bun EXECUTABLE` outside the Dori it may replace. The controller directory is a stable link to the accepted controller release; each cycle invokes the actual `upstream check`, so the next cycle loads accepted code. When the link changes, the supervisor exits for the service manager to reload itself. It uses `intervalSeconds` from the config, does not manufacture status messages, and never retries a model merely because the interval elapsed. Completed detector unavailability (exit `4`) and a lock held by a verified live controller (exit `5`) wait for the next interval rather than disabling the service; configuration errors and malformed, stale or unverifiable locks still stop it. Unfinished ambiguous model work remains held; only finished ready promotion effects have automatic readback-based recovery.

On Linux, `SIGUSR1` wakes the supervisor's next check without interrupting an active cycle. An expiring initial quiesce checkpoint can therefore be consumed immediately rather than waiting a full polling interval. The signal does not bypass deployment, publication or review gates.

[`examples/update-supervisor.service`](../../../examples/update-supervisor.service) supplies an outside-session systemd user unit for the layout `~/.dori/update/{config.json,controller}` and `~/.dori/toolchains/bun-1.4.4/bun`. Provision that private Bun and the trusted controller link explicitly, configure publication/runtime identities and protected monitor launchers, and install the unit as `~/.config/systemd/user/dori-upstream-update.service` before `systemctl --user enable --now dori-upstream-update.service`. This does not upgrade global Bun. Exclude generated releases/toolchains/jobs from unrelated home-backup source tracking. Systemd supervision does not silently recreate an unavailable unrelated herdr server.

Use only trusted upstream and configured commands: source/process/environment separation is not an OS sandbox. First exercise a real nonempty upstream delta, exact-source checks/fresh review, publication readback, native restart, monitor/intake continuity and failed-start rollback in owned fixtures. If replaying an authentic historical change because upstream has no new revision, report that fact; an unchanged-head `stage` is not evidence that a new update was automatically ported.
